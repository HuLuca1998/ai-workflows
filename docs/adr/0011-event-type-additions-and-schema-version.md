# 11. 新增事件类型不升 schemaVer；它留给记录形状的破坏性变更

日期：2026-08-01 · 状态：已接受

## 背景

`events.ts` 原来写着「新增类型属于契约变更：必须同时升 schemaVer 并更新
docs/adr」。2026-08-01 新增 `system.worktree_cleaned` 时两路独立复核都指出
这条规则被违反了 —— 但追下去发现规则本身与机制脱节：

- `RUN_EVENT_SCHEMA_VERSION` 恒为 1，**没有任何读取侧消费它做兼容**。
  升到 2 只是仪式，不改变任何行为。
- 真正的兼容边界在前端的 `z.enum(RUN_EVENT_TYPES)`：**旧**客户端连**新**
  服务端时，不认识的新类型会让整页事件流被拒收。

## 决定

1. **新增事件类型不升 schemaVer**。桌面形态前后端同包发布，不存在
   版本错配；Web 形态（O-2）开工时要先解决「旧客户端对未知枚举值的
   容忍」（把 `type` 的校验从 enum 收窄改为「认识的投影、不认识的原样
   列出」），那是读取侧的活，不是版本号的活。
2. `RUN_EVENT_SCHEMA_VERSION` 保留，语义收窄为：**事件记录本身的形状**
   （字段增删改语义）发生破坏性变更时递增。枚举值的增加不算。
3. 新增事件类型的门禁照旧：九类前缀约束（`contract_sync_test`）、
   发射点双向白名单（`event_emission_test`）、生成物一致（`contracts:check`）。

## 代价

在 Web 形态真的存在独立部署的客户端之前，「旧客户端撞见新事件类型」
的场景没有防线 —— 这是已知欠账，记在 O-2 的开工条件里。
