# ADR-0008：结构化 Patch 连同结果图一起提交

- 状态：**已被取代**（2026-07-29，见 [ADR-0009](0009-engine-applies-patch.md)）
- 日期：2026-07-27

> 退出条件在本文末尾就写着，系统级 MCP 触发了它：Agent 从 HTTP 连进来时
> 中间没有任何客户端，没人替它算结果图。Rust 侧已实现 applyPatch，
> `graphJson` 降级为可选的交叉校验。

## 背景

契约里 `workflow.patch` 的语义是「提交一批结构化操作，引擎应用后返回 Diff 与校验结果」。
但结构化 Patch 的应用逻辑（`applyPatch`）实现在 `packages/contracts`（TypeScript），
引擎侧（Rust）没有对应实现，短期也不打算再写一份——两份实现必然漂移，
而漂移的后果是「同一批操作在两边算出不同的图」，这比任何性能问题都严重。

## 决策

调用方（画布 / 主管 AI / MCP）在客户端应用 Patch，算出 **Diff、校验结果、结果图**，
然后把结果图随 `graphJson` 一并提交。引擎负责两件事：

1. `baseRevision` 守卫（必须在引擎侧，才对并发安全）
2. 把结果图作为新修订落库

## 这算不算「整份回写」

不算。ADR-0003 禁止的是**绕过结构化 Patch 与 Diff 的整图覆盖**——
那样用户在确认前看不懂 AI 到底改了什么，出问题也无法解释。

这里的链路仍然是：结构化操作 → 应用 → 生成可视化 Diff → 用户确认 → 提交。
`graphJson` 只是把已经算好的结果捎带过去，避免同一套逻辑写两遍。
守卫（版本）与审计（操作列表）都还在。

## 代价与边界

- 引擎必须信任调用方传来的图。缓解：`graphJson` 落库前要过一遍图 Schema 校验；
  跨进程边界上，结构化操作列表仍然一并提交并写入审计事件，出问题时可以对着操作重放。
- 一旦引擎侧要独立应用 Patch（例如 M4 让 MCP 直连引擎而不经过客户端），
  就该在 Rust 侧实现 applyPatch，并把 `graphJson` 降级为可选校验用途。
  字段设计成 optional 就是为了留这条路。
