# ADR-0005：运行状态由事件流投影，不另存状态表

- 状态：已采纳
- 日期：2026-07-27

## 背景

执行记录有三种视图：对话（面向理解的时间线）、事件（九类分类流）、产物。
再加上节点进度、运行状态、审批横幅。

最直接的做法是各存各的：一张 run 表存状态，一张 node 表存进度，
消息单独一张表。

## 决策

**RunEvent 是唯一事实来源。** 所有视图都是同一条流的投影：

```
EventStore.conversation()   → 对话视图
EventStore.byCategory()     → 事件视图
EventStore.artifacts()      → 产物视图
EventStore.nodeProgress()   → 节点进度
EventStore.runStatus()      → 运行状态
EventStore.provenance()     → 用了哪个模型 / 提示词 / 记忆、谁批准了什么
```

界面不允许从消息文本里拼接状态字段，也不允许各自查库。

## 理由

- 「可解释优先」要求任何时刻都能回答「现在跑到哪、为什么停」。
  多份状态一旦不一致，这个问题就答错了，而且很难发现
- 恢复能力天然得到满足：重启后重放事件就得到当前状态
- 审计免费：每个状态变化本来就是一条带 actor 与时间戳的事件

## 落地约束

- `(run_id, seq)` 在存储层唯一，seq 由存储分配，保证连续
- 事件只存摘要与引用；大 payload 落 `artifacts/`（摘要超 2000 字符直接拒收）
- `EventStore` 去重、按 seq 归并、检测空洞——传输层重连重发是常态

## 代价

- 长运行的事件量会膨胀：靠摘要 + 引用、分块日志、上限截断、可配置保留策略缓解
- 查询「当前状态」要重放。缓解：`run` 表冗余一份当前状态用于列表页，
  但它是投影的缓存，不是真源——冲突时以事件流为准
