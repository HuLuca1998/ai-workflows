Architecture

技术选型（Web + macOS App 双形态）

打开完整选型文档
UI 层 · 一套 React 代码，两种壳
React 18 + TypeScript + Vite；桌面用 Tauri 2 WebView（体积小、原生通知与 Keychain 直通），Web 用同一构建产物。状态 Zustand + TanStack Query，画布 XYFlow，虚拟化 TanStack Virtual，样式 Tailwind + CSS 变量主题。
传输层 · 事件优先
桌面走 Tauri IPC + event channel；Web 走 tRPC over HTTP + SSE。前端只订阅 RunEvent 流，Conversation / Console / Run Detail 都是同一事件流的投影。
引擎层 · Rust 编排 + Node 适配
Rust（Tokio）负责调度、检查点、路径守卫与进程隔离；ACP Adapter 用 Node 侧 sidecar 对接 Claude Code / Codex。SQLite（WAL）+ FTS5 存事件与索引，大产物落 Artifact 目录，Secret 只留 Keychain 引用。
AI 的深度读写：Core API 在下，MCP 在上
唯一执行写操作的是内部 Workflow Core API：baseRevision 版本守卫、结构化 Patch、Scope 校验、Diff 与审计事件。MCP Server 只是它面向 Agent 的适配层，本地 HTTP/tRPC 面向脚本与 Web。不开放直连数据库。
workflow.get / diff / validate workflow.create / patch memory.list / create / update / delete publish / run 稳定后再开
为什么不是 Electron
本地优先工具对内存与启动时间敏感；Tauri 包体 ~15MB、常驻内存约为 Electron 的三分之一，且能直接用 Rust 做路径守卫与子进程沙箱。代价是 WKWebView 兼容性需自测，Node 生态需以 sidecar 引入。
为什么不是纯 SwiftUI
你要求同时支持 Web。SwiftUI 画布与 Web 端需两套实现，维护成本翻倍。折中方案：壳与系统集成（通知、快捷指令、菜单栏）用原生 API，业务界面共用 React。
