AI Workflows · 客户端技术选型
v0.1 草案 · macOS App + Web

本文给出客户端（界面层到本地引擎）的技术方案。约束来自产品文档：本地优先、显式权限、草稿与执行分离、事件流是唯一事实来源、可恢复；并按你的要求同时支持 macOS App 与 Web 两种形态。

1. 结论摘要

层选型理由与取舍
界面React 18 + TypeScript + Vite一套业务界面同时服务桌面与 Web；生态成熟，画布与虚拟化库齐全。
桌面壳Tauri 2（Rust + WKWebView）包体约 15 MB、常驻内存约为 Electron 的 1/3；路径守卫、子进程隔离、Keychain 直接用 Rust 实现。代价：WKWebView 兼容性需自测，Node 生态以 sidecar 引入。
画布XYFlow（React Flow 12）+ 自定义节点端口、连线、选区、minimap 与虚拟化开箱即用；节点外观完全自绘，避免“像 n8n”。百节点以上再加视口裁剪。
状态Zustand（本地 UI）+ TanStack Query（服务端态）画布高频拖拽用不可变 store 会抖动；Zustand 局部订阅更稳。
样式Tailwind + CSS 变量主题令牌令牌与设计系统同源，支持深浅色与 Increase Contrast。
编排引擎Rust（Tokio）调度、检查点、重试、路径 canonicalize 与沙箱在同一进程内完成，不经过 JS。
Agent 适配Node sidecar 跑 ACP AdapterClaude Code / Codex 的官方生态在 Node；以子进程 + JSON-RPC 隔离，崩溃不影响主应用。
存储SQLite（WAL）+ FTS5 + Artifact 目录事件、Run、Workflow 版本入库；大日志与二进制落盘，事件只存引用。
凭据macOS Keychain（Web：OS keyring / KMS）数据库只存 credentialRef，导出默认为占位符。
传输桌面 Tauri IPC + event channel；Web tRPC + SSE两端都是“订阅 RunEvent 流”，界面代码不感知差异。

2. 分层架构

UI（React）　Studio · Canvas · Inspector · Conversation · Run Detail · Settings
　　│ 只读 RunEvent 投影 / 发命令，不直接碰文件与进程
Client Core（TS）　EventStore 订阅 · 乐观草稿 · Schema 校验 · 权限提示
　　│ Tauri IPC ┆ tRPC over HTTP + SSE
Engine（Rust）　Scheduler · Checkpoint · Env 快照 · PathGuard · Redactor
　　├ Script Runner（zsh / python，非交互，超时与输出上限）
　　├ Git Service（worktree 创建、登记、清理策略）
　　└ ACP Sidecar（Node）→ Claude Code / Codex
Storage　SQLite(WAL)+FTS5 · Artifacts · Keychain 引用

3. 界面层关键决策

事件投影而非多套数据。Conversation、Run Console、Run Detail 共用一个 RunEvent 流，按 sequence 归并，前端只做过滤与折叠；不允许从消息文本里拼接状态字段。

草稿与已发布分离。画布编辑落在 draft store，发布时生成不可变 WorkflowVersion；运行记录始终引用版本号与配置哈希。

节点配置走居中弹层。画布保持完整可视，弹层承载 Prompt、权限、重试等长表单；配置 Schema 驱动渲染（JSON Schema → 表单），新节点类型不需要改 UI 代码。

AI 以浮层召唤。⌘K 唤起，携带当前 run / 节点上下文；AI 的工作流修改一律先出 Diff 再落草稿。

审批双通道。画布节点高亮 + 顶部横幅提示位置，浮层与 Run Detail 承载完整决策表单，保证“醒目但不打断上下文”。

5. 安全实现要点

  • 路径先 canonicalize 再判断是否位于授权根目录；拒绝根目录、Home、未解析变量与宽泛 glob；单独防护符号链接逃逸。
  • Agent 的 cwd 由引擎决定，Prompt 不能改变安全边界；能力声明（文件 / 命令 / 网络 / Secret）在引擎侧强制。
  • Secret 只在执行目标节点时注入子进程，不写入持久化环境快照；stdout、stderr、AI 输入输出统一过 Redactor 后才落库。
  • Commit / Push / PR / 删除等外部写操作必须由审批结果授权，重试前先核对外部实际状态。

6. MCP 还是 API：两层，不是二选一

AI 的深度读写能力必须落在一套内部 Workflow Core API 上：它是唯一执行写操作的入口，负责 baseRevision 版本守卫、结构化 Patch（addNode / connect / setConfig，而不是回写整份 JSON）、能力 Scope 校验、Diff 生成与审计事件。UI、MCP、HTTP 都只是它的调用方。上层再决定对外暴露成什么。

出口给谁用为什么
MCP Server（首选，首版做）Claude Code / Codex / Claude Desktop 等 Agent工具可自动发现、可逐工具授权、可撤销；Agent 生态原生支持，不用为每个客户端写胶水。Scope 与 Keychain 绑定：workflow:read、workflow:write-draft、workflow:publish、workflow:run、memory:read/write。
本地 HTTP / tRPC API脚本、CI、快捷指令、Web 形态、第三方集成MCP 不适合非 Agent 调用方；同一 Core 暴露 OpenAPI，带 token 与同样的 Scope 校验。
直连数据库 / 文件不开放绕过版本守卫与审计，AI 一旦写坏无法解释和回滚。

落地顺序：Core API → MCP（只读 + create + patch + validate + 记忆 CRUD）→ 稳定后再开 publish / run → Web 形态时顺带暴露 HTTP。无论走哪条路，修改现有草稿一律先出可视化 Diff 由用户确认；删除、发布、扩权、新增外部写操作必须单独确认。

7. Web 形态的差异

能力macOS AppWeb
本地文件与 worktree原生，授权目录需自托管 Agent（用户机器上跑引擎），浏览器只当界面
通知User NotificationsWeb Push，降级为站内提醒
凭据Keychain服务端 keyring / KMS，浏览器不持有明文
快捷入口快捷指令 / URL Scheme / 菜单栏URL 参数与快捷键

建议：Web 首版定位为“同一引擎的远程界面”，不承诺纯浏览器执行本地命令，避免安全模型分裂。

9. 主要风险

风险缓解
ACP Adapter 版本漂移导致 Session 失效启动时跑兼容性探针；Session 不可恢复时明确告知“已用结构化状态重建”，不伪装连续
WKWebView 与 Chromium 行为差异画布与虚拟化在两端各跑一次基准；CI 加 Safari Tech Preview 冒烟
大 Run 事件量膨胀事件只存摘要与引用，日志分块 + 上限截断，保留策略可配置
Rust 团队人手M1 引擎可先用 Node 原型跑通契约，M2 再迁移；IPC 契约先冻结

11. Core API 契约（IPC / tRPC 共用）

方法入参 → 出参
workflow.list / get{query?} → 列表；{id, rev?} → {graph, rev, versions[]}
workflow.patch{id, baseRevision, operations[]} → {rev, diff, validation}；rev 不匹配返回 REVISION_CONFLICT
workflow.validate{id, rev} → {ok, issues[]{level,nodeId,code,message}}
workflow.publish{id, rev} → {versionId, version, configHash}
run.start{workflowId, versionId|draftRev, inputs, workdir} → {runId}（先做 preflight）
run.events{runId, fromSeq, types?[], limit} → 事件页；订阅版为 SSE / channel 推送
run.resume / cancel / retryNode{runId, nodeId?} → {runId, newAttempt}
approval.decide{runId, nodeId, decision, selected[], supplement} → {accepted}
memory.* / prompt.* / model.* / agent.*标准 CRUD，写操作携带 ver 做乐观锁
env.health / env.install→ 健康报告；{tools[]} → 安装进度事件流

统一错误对象：{code, message, retriable, hint}；错误码分类 VALIDATION / PERMISSION / REVISION_CONFLICT / RUNTIME / TIMEOUT / EXTERNAL / INTERNAL。所有写方法记审计事件。

13. 状态机与并发

Run：Created → Preflight → Queued → Running →（Waiting Approval | Paused | Interrupted → Resuming）→ Succeeded / Failed / Cancelled。Node：idle → queued → running → waiting → succeeded / failed / cancelled / skipped，每次重试产生新 attempt。调度器按连线拓扑推进：1→N 并行分发（受全局 Agent 进程上限与节点级并发上限约束）、N→1 依据汇聚策略（全部 / 任一 / Quorum / 顺序）阻塞、N→N 全部就绪后再分发。子工作流以独立 Run + parent_run_id 表达，审批冒泡到父运行。

14. 质量门禁

  • 单元：PathGuard（逃逸用例）、Redactor（Token / Header / 正则）、结构化 Patch 应用与 revision 守卫、汇聚策略。
  • 集成：引擎跑通内置示例（脚本 + 审批 + worktree + ACP mock），断电模拟后可恢复到同一检查点。
  • 契约：Core API 类型由单一 schema 生成，UI 与 MCP 共用；CI 校验 MCP 工具不得绕过 Core。
  • 性能基准：200 节点画布拖拽、10 万事件滚动、流式输出帧率，WKWebView 与 Chromium 各跑一次。
  • 安全回归：导出物、事件、预览中不得出现 Secret（正则扫描 + 人工抽检）。
