# 端到端测试

单元测试测「这段代码对不对」，端到端测「装好的应用真能干活吗」。
两者抓到的问题不一样 —— 下面七个缺陷全是端到端跑出来的，
当时单元测试全绿。

## 三层，可重复运行

| 层                             | 规模      | 测什么                                        |
| ------------------------------ | --------- | --------------------------------------------- |
| `tests/e2e/api_e2e.py`         | 60 项断言 | 真起进程、真建 worktree、真并发、真取消       |
| `tests/e2e/*.spec.ts`          | 39 条用例 | 真实点击 → HTTP 桥接 → 真实引擎               |
| `tests/e2e/github_scenario.py` | 15 项断言 | 读 Issue → worktree → 改代码 → 推分支 → 开 PR |

前两层进了 CI，每次推送自动跑；失败时上传 Playwright 报告与失败截图 ——
CI 里最怕的是「看不到当时页面长什么样」。

GitHub 全流程那套不进 CI：它需要仓库写权限，会留下真实的 PR。

## 怎么跑

```bash
# 1. 起开发用的 HTTP 桥接（复用桌面版同一套 core-api）
pnpm dev:server -- --port 5177 --db /tmp/aiwf-e2e/aiwf.sqlite

# 2. API 层
python3 tests/e2e/api_e2e.py --workdir /tmp/aiwf-e2e/runs
python3 tests/e2e/api_e2e.py --workdir /tmp/aiwf-e2e/runs --repo /path/to/git/repo

# 3. 真实 GitHub 全流程（需要 gh 已登录且有写权限）
python3 tests/e2e/github_scenario.py --repo /path/to/repo --issue 1

# 4. 浏览器层
VITE_AIWF_SERVER=http://127.0.0.1:5177 pnpm dev    # 另开一个终端
pnpm test:e2e
```

## 第四层：人工 / AI 驱动的界面审查

上面三层是**自动化**的：它们只回答「我写的断言成不成立」。
回答不了的问题有一整类——拖起来卡不卡、翻页找不找得到、
这个东西看着能点其实点不动、图纸上有的实现里有没有。

那一类交给 [ui-cases/](ui-cases/README.md)：**25 份剧本，由 Claude 逐份执行**
（用浏览器工具真的打开页面点，不靠读代码推断）。

| 目录                                              | 内容                                                                                                     |
| ------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| [ui-cases/README.md](ui-cases/README.md)          | 总纲：环境、浏览器工具怎么用、卡顿/可发现性/响应的量化判据、三问法                                       |
| [ui-cases/personas/](ui-cases/personas/README.md) | 六个角色：前端 3（界面体验 / 交互健壮性 / 前端代码审查）+ 后端 3（契约 API / 引擎存储 / 安全与可解释性） |
| `ui-cases/01…17-*.md`                             | 十七份模块地图：每一屏有什么元素、每个东西点下去该怎样、边界在哪                                         |

角色带视角（横跨所有屏），模块地图带元素清单（每屏一份）。
执行时先读自己那份角色剧本，再按它指定的屏去翻模块地图。

## 为什么要有这一层

桌面壳跑在 WKWebView 里，浏览器工具驱动不了它。
`aiwf-devserver` 把同一套 `aiwf-core-api` 用 HTTP 暴露出来，
浏览器就能操作真实引擎 —— 测的是桌面版跑的那套逻辑，不是替身。

**只用于本地开发与测试**：无鉴权、只绑 127.0.0.1。
生产的 Web 形态（M6）走 tRPC + SSE + 会话鉴权。

`crates/core-api/tests/parity_test.rs` 守住两端命令表一致：
漏注册一个命令不会编译报错，症状是「桌面版好用、Web 版某个按钮没反应」。

## 端到端抓到的缺陷

| #   | 缺陷                       | 症状                         | 为什么单元测试没抓到                          |
| --- | -------------------------- | ---------------------------- | --------------------------------------------- |
| 1   | 失败的脚本不留日志产物     | 脚本失败时看不到 stderr      | 产物测试只覆盖成功路径                        |
| 2   | 并发写事件 seq 冲突        | 取消运行时偶发「数据库错误」 | 单元测试是单线程的，竞态窗口不存在            |
| 3   | 终态被推进覆盖回 running   | 取消后运行停不下来           | 要特定时序，8 轮里出现 1 次                   |
| 4   | 界面用了自造的 runtime 值  | 保存模型没反应               | 组件测试 mock 掉 coreClient，Zod 校验一起绕过 |
| 5   | Rust 的 None 序列化成 null | 整页「返回值不合契约」       | 契约的 `.optional()` 只接受字段缺席           |
| 6   | 事件被重复渲染             | 同一条事件显示两遍           | `select()` 与轮询并发拉同一个 fromSeq         |
| 7   | 悬空的连线                 | 删节点后图立刻校验不过       | 只有真的点「删除」才会发生                    |

还有两个可用性问题：默认工作目录带 `~` 且不展开、
引擎自己的运行目录不存在却报错 ——
都会让用户「打开启动表单什么都不改就无法运行」。

## 每类缺陷留下的守卫

修 bug 之外，每一类都留了防止复发的机制：

| 守卫             | 位置                                            | 防的是                            |
| ---------------- | ----------------------------------------------- | --------------------------------- |
| 契约校验替身     | `apps/web/tests/_contractClient.ts`             | #4：mock 绕过 Zod                 |
| Option 字段检查  | `crates/core-api/tests/parity_test.rs`          | #5：新 DTO 漏 skip_serializing_if |
| 两端命令表一致   | 同上                                            | 漏注册命令（不会编译报错）        |
| 接入方式枚举同步 | `crates/engine/tests/contract_sync_test.rs`     | Rust 侧枚举脱离契约               |
| 并发写事件       | `crates/store/tests/store_test.rs`              | #2：4 线程 × 25 条，seq 无缺口    |
| 终态不可覆盖     | 同上                                            | #3                                |
| 事件去重         | `apps/web/tests/runs-store.test.ts`             | #6                                |
| 测试文件位置     | `packages/contracts/tests/repo-hygiene.test.ts` | 源码旁的测试静默不跑              |

## 真实 GitHub 场景

`tests/e2e/github_scenario.py` 是图纸「GitHub Issue 修复」那条主线的
可执行版本：AI 节点（分析 / 执行 / 审查 / 决策）留给 M3，
其余每一步都是真的 —— 真调 gh 读 Issue、真建 worktree、真改代码、
真推分支、真开 PR。

它验证的几件事单靠单元测试证明不了：

- **审批前外部世界没被动过**：主仓库工作区干净，远端还没有这个分支
- **批准后才发生外部写操作**：分支推上去、PR 开出来
- **每个节点都留下 succeeded 事件**：8 个节点全在事件流里
- **跑完自己收拾干净**：关 PR、删远端分支、移除 worktree

夹具仓库是 `HuLuca1998/aiwf-e2e-fixture`（私有），
里面留了一个可复现的缓存失效缺陷。

## 性能数字

| 项                    | 结果        | 来源             |
| --------------------- | ----------- | ---------------- |
| 200 节点画布打开      | 627 ms      | `stress.spec.ts` |
| 200 节点画布拖动帧率  | 76 fps      | 同上（Chromium） |
| 40 节点工作流完整执行 | < 3 s       | 同上             |
| 6 万行脚本输出        | 截断到 1 MB | 同上             |

WKWebView 侧的帧率还没测 —— 两个渲染引擎的表现不能互相代替。

## 测试数据

跑测试会在 `--workdir` 下留下真实的运行目录、产物与 SQLite 库，
`--repo` 指向的仓库里会真的建 worktree 和分支（用完自动清理）。
这些数据保留着，出问题时可以直接翻。
