# UX 自由使用记录：中断、恢复与多标签

测试时间：2026-07-28（Asia/Singapore）  
测试方式：Playwright + Chromium，实际操作 `http://localhost:5173`；主要使用 1365×900，另在 1024×768、768×768、390×844 下缩窄窗口。  
测试数据：我通过界面新建并重命名了工作流「Codex 中断恢复测试 20260728-1324」（`wf_18c65c94abf73728`），并使用运行 `run_0cf2a36bbb9ffe34` 验证详情恢复。本轮刻意避开上一轮的常规创建—运行路径，集中体验“工作被刷新、断网或另一个标签打断后，能不能安全回来”。

## 🔴 走不通

### 1. 刷新页面不提示，未保存的整张草稿直接消失

复现：

1. 打开「Codex 中断恢复测试 20260728-1324」。
2. 从左侧依次拖入「入口设置」和「结束」，先不要点“保存草稿”。
3. 确认工具栏显示“保存草稿”，校验摘要显示“校验通过 · 2 节点 0 连接”。
4. 直接刷新浏览器页面。

实际：没有离开确认框，也没有自动恢复；刷新后画布变回 0 个节点，摘要变成“1 个问题 · 0 节点 0 连接”，按钮却显示“已保存”。刚才两个节点无法找回。

期望：至少用浏览器离开确认保护脏草稿；更理想的是把未保存内容暂存到本地，刷新后提供“恢复草稿 / 放弃”选择。“已保存”不能出现在内容刚丢失的状态下。

### 2. 保存时网络瞬断会清空本地修改，恢复网络后也无处重试

复现：

1. 打开一个 0 节点的草稿，拖入「入口设置」，确认画布为 1 个节点且“保存草稿”可点。
2. 用 Playwright/DevTools 只在点击保存时中断 `**/ipc/**` 请求（本次实际失败的是 `workflow_save_draft`），不要停止后端服务。
3. 点击“保存草稿”，看到连接失败提示后恢复网络。

实际：页面提示“连不上开发服务 http://127.0.0.1:5177（先跑 pnpm dev:server 起 aiwf-devserver）”，但同时把画布从 1 个节点重置为 0 个节点，按钮变成禁用的“已保存”。恢复网络后没有“重试保存”，原修改也已经不在，刷新仍是 0 节点。

期望：保存失败时保留当前画布和 dirty 状态，明确显示“保存失败”，并提供重试。网络错误不应触发用服务端旧稿覆盖本地编辑现场。

### 3. 多标签冲突虽然阻止了旧版本覆盖，但把冲突标签里的修改一起丢掉

复现：

1. 用两个标签 A、B 同时打开同一个 rev0、0 节点工作流。
2. A 拖入「入口设置」并保存；A 成为 rev1。
3. 不刷新 B，在 B 的旧 rev0 上拖入「结束」并保存。

实际：B 正确提示“草稿已变化：基础版本 0，当前 rev 1”，A 保存的「入口设置」没有被覆盖；但 B 刚拖入的「结束」立即从画布消失，B 回到 0 节点现场。界面没有保留冲突副本、复制 JSON、重新应用或合并入口。

期望：冲突提示出现时必须先保住 B 的本地修改，例如保留画布并让用户“刷新服务端版本 / 另存副本 / 复制本地改动”。检测到冲突后直接清场，会让正确的并发保护变成另一种数据损失。

## 🟡 能用但别扭

### 1. 运行详情没有可恢复的 URL，刷新后要重新在长列表里找

复现：

1. 打开“执行记录”，点任意一条运行；本次点了「UI 测试 · 打招呼」。
2. 确认右侧已显示参数、11 条事件和 Run ID `run_0cf2a36bbb9ffe34`。
3. 观察地址仍为 `/runs`，然后刷新页面。

实际：刷新后 Run ID 和完整详情全部消失，右侧恢复成“选一次运行，这里会显示它的完整记录”。URL 没记录选中的运行，因此也无法收藏、复制链接给同事或用浏览器前进/后退回到该详情。在本次 655 条运行数据下，重新定位成本很高。

期望：选中运行后把 Run ID 写进路由，例如 `/runs/run_0cf2a36bbb9ffe34` 或查询参数；刷新、分享链接和浏览器历史都应恢复同一条详情。

### 2. 768px 宽窗口仍能操作，但编辑器工具栏被挤成竖排字

复现：

1. 打开上述工作流编辑器。
2. 把浏览器窗口缩到 768×768。

实际：画布和节点库仍能用，但工作流名称折成两行；“版本”“已保存”“发布版本”“运行”被压到约 48–56px 宽，中文逐字换行，其中“已保存”按钮高到约 71px，工具栏高度和扫读节奏明显失衡。继续缩到 390×844 时，主操作实际位于视口右侧约 x=499–718，却没有可用的横向滚动入口。

期望：窄窗口下把次要动作折叠进菜单，或明确设置可滚动的最小桌面宽度并提示用户；不应静默裁掉主操作。若产品明确不支持此宽度，也应该给出支持范围提示。

## 🟢 细节

### 1. 站内跳转再后退，未保存草稿仍在

复现：拖入一个「入口设置」但不保存，点侧栏“执行记录”，再使用浏览器后退。

结果：回到原编辑器后仍是 1 个节点，“保存草稿”仍可点，站内导航没有立刻清掉编辑现场。这种连续性很好；只需把同样的保护补到刷新、关闭和保存异常路径。

### 2. 并发版本检查确实保护了服务端的新草稿

复现：按上面的多标签步骤，让 B 用 rev0 保存，而 A 已经保存为 rev1；随后刷新 A。

结果：A 刷新后仍保留「入口设置」，没有被 B 的旧版本覆盖；冲突信息同时给出了基础版本 0 和当前 rev 1，原因是可理解的。问题在冲突后的本地恢复，不在冲突检测本身。

### 3. 工作流重命名轻量且持久

复现：双击编辑器标题，把“未命名工作流 51”改成「Codex 中断恢复测试 20260728-1324」，按 Enter，再关闭浏览器并用直达 URL 重新打开。

结果：名称成功保留；双击就地编辑、Enter 提交的路径短，不需要打开额外抽屉。

## 处理结果（Claude 回填）

三条 🔴 是同一个根因的三个入口：`DraftStore.commit()` 的 catch 无条件把本地图退回
`committedGraph` 并清空 `pending`。网络瞬断时服务端根本没收到，本地状态完全有效，
却被丢了；界面还因为 `isDirty` 变 false 而显示禁用的「已保存」——数据丢了，提示说一切正常。

| 编号                        | 结论 | 处理                                                                                                           |
| --------------------------- | ---- | -------------------------------------------------------------------------------------------------------------- |
| 🔴 1 刷新丢草稿             | 属实 | `EditorPage` 加 `beforeunload` 保护（dirty 时才拦，unmount 摘干净）；3 条用例                                  |
| 🔴 2 网络瞬断清空修改       | 属实 | `commit()` 不再回滚，失败后 `isDirty` 仍是 true，按钮显示「保存草稿」可重试；2 条用例                          |
| 🔴 3 冲突清场               | 属实 | 同上保留本地图，另加 `discardLocal()` 作为用户主动脱身的出路，接到报错条上；4 条用例                           |
| 🟡 1 运行详情没有可恢复 URL | 待办 | 图纸没有 `/runs/:id` 路由，需要先确认；当前用 `?run=` 查询参数进详情（启动后跳转就是这么走的），刷新恢复还没接 |
| 🟡 2 768px 工具栏挤成竖排   | 待办 | 图纸是桌面形态，未定义窄窗口降级；要改先确认支持范围                                                           |

## 本轮结论

当前最值得优先处理的是“任何失败都不能清掉用户尚未保存的现场”：刷新、网络错误和版本冲突是三种不同入口，却都能造成不可恢复的数据损失。已有的 dirty 状态、站内后退保留和 rev 冲突检测说明基础信号都在；下一步应统一成离开保护、本地暂存、失败重试和冲突副本四个恢复能力。运行详情路由和窄窗口工具栏属于随后可改善的工作连续性问题。
