## 第 3 轮 · hint 在中间层被丢

第 1 轮报告里我写「这条值得下一轮实测」，实测证实了。

引擎返回的是完整的：

```json
{
  "code": "REVISION_CONFLICT",
  "hint": "别处已经把它改到 rev1，而你这次基于 rev0。刷新拿到最新版本再改一次",
  "message": "草稿已变化：基础版本 0，当前 rev 1",
  "retriable": true
}
```

而界面上（两个标签页制造真实冲突）只有：

> 草稿已变化：基础版本 1，当前 rev 2　[放弃本地改动]

**hint 不见了。** 定位到 `ipc-mapping.ts:488` 的 `normalizeIpcError` ——
重建 `CoreApiError` 时只读 code / message / retriable。

这正是第 5 轮 B1 预言过的：「即使将来 Rust 补上 hint，也会在这一层被丢掉 ——
当下看不出症状、补了上游也不生效」。上游补了，坑就生效了。

修完之后界面上是：

> 草稿已变化：基础版本 2，当前 rev 3**（别处已经把它改到 rev3，而你这次基于 rev2。刷新拿到最新版本再改一次）**　[放弃本地改动]

顺带核实了同批的另外三条：`describeError` 已统一到一个文件、
`PlaceholderPage` 已删除、中文标识符已清零。
**`retriable` 仍然没有任何消费方**（`apps/web/src` 里一处都没读它）——
记为建议，加「重试」按钮属于图纸没规定的改动。

## 第 4 轮 · 并发运行共用一个工作目录

补第 5 轮 B2 中断没做的并发部分。并发起 5 个运行，
每个 `echo "${input.tag}" > mark.txt` 再读回。

**seq 全部连续无缺口、每个运行内唯一** ✅

**但磁盘上只有一个 `mark.txt`**，内容是 `'并发-1'` —— 5 个运行写的是同一个文件。

| 出处                        | 说的话                                                                   |
| --------------------------- | ------------------------------------------------------------------------ |
| 启动表单 `LaunchDialog:231` | 「留空则用应用的运行目录。**每次运行一个独立目录，并行运行互不影响。**」 |
| `Runner::workdir` 注释      | 「这是引擎自己的运行目录（**每个 Run 一个**）」                          |
| 实际 `resolve_workdir`      | 未指定时**所有运行都返回 `data_dir/runs`**                               |

而 M2 出口标准里那条「同一工作流不同参数并行运行互不影响」，
`supervisor_test` 是**显式传不同 workdir** 验的 —— 恰好绕开了产品的默认路径。

**修**：新增 `resolve_run_workdir`，未指定时在运行根下开 `run-<时刻>-<序号>`；
显式指定的原样使用（那通常是「跑在我这个仓库里」，再套一层就跑错地方）。
Dry Run 仍用 `resolve_workdir` 拿根目录 —— 一次预检不该建一个空的运行目录。

新增 [`crates/core-api/tests/workdir_test.rs`](../../crates/core-api/tests/workdir_test.rs) 三条：
每个运行各得一个 / 仍在应用运行目录之下 / 显式指定不被拆成子目录。

复验（重启 devserver 载入新代码后）：

```
并发-1  succeeded  run-1785254238886-0000   mark.txt = 并发-1  ✓
并发-2  succeeded  run-1785254238886-0001   mark.txt = 并发-2  ✓
并发-3  succeeded  run-1785254238886-0003   mark.txt = 并发-3  ✓
并发-4  succeeded  run-1785254238886-0002   mark.txt = 并发-4  ✓
并发-5  succeeded  run-1785254238886-0004   mark.txt = 并发-5  ✓

内容错配数: 0
```

## 第 5 轮 · 产物预览是明文密钥

跑一条 `echo "token=sk-TESTLEAK-…"` 的脚本，四条路径逐个查：

| 路径         | 结果                                               |
| ------------ | -------------------------------------------------- |
| 启动参数     | ✅ 库里存的是 `{"token":"[已脱敏]"}`，写入时就脱敏 |
| 事件流       | ✅ 11 条事件，0 条含明文                           |
| 诊断包       | ✅ `grep TESTLEAK` = 0，产物只列元信息             |
| **产物预览** | ❌ **一字未改的明文**                              |

```
token=sk-TESTLEAK-1234567890abcdefghijklmnopqrstuvwxyz
AWS_SECRET_ACCESS_KEY=TESTLEAKaws1234567890
```

而事件流底部常驻着「Secret 值在写入事件存储前已脱敏，**界面不提供绕过查看**」——
产物就在隔壁那个 tab，每条都有「预览」按钮，那是最容易被截图与录屏的地方。

> 过程中我自己犯过一次错：第一次用了错的命令名（`run_artifactContent`），
> 拿到 400 却把空字符串当成「不含密钥」，差点得出反向结论。
> 用正确的 `run_artifact_content` 重测才看到真相。

**修**：产物预览过 `Redactor::with_defaults()`。磁盘上的文件不动 ——
那是脚本的真实输出，要调试就去 workdir 看（路径在运行详情页显示着）。

新增 [`crates/core-api/tests/artifact_redact_test.rs`](../../crates/core-api/tests/artifact_redact_test.rs) 两条：
不把明文送到界面 / 不含密钥的产物原样返回（脱敏器不能把普通日志改得面目全非）。

复验：

```
token=[已脱敏]
AWS_SECRET_ACCESS_KEY=[已脱敏]
done
```
