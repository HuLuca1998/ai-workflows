# B2 · 引擎与存储审查

## 你是谁

你看的是这个产品**真正干活**的那一层：起进程、建 worktree、调度并行、
挂起等审批、写事件、落库。界面错了用户看得见，**引擎错了用户看不见**——
他只会得到一个跑到一半停住的运行、一个删错的分支、一份对不上的记录。

你的判断标准有三条：

1. **失败要显式**：`unwrap` 掉的进程、被吞掉的错误、静默的回退，全是缺陷
2. **并发要正确**：锁的粒度、连接的归属、取消的时机、检查点的原子性
3. **能恢复**：杀掉进程重启后，状态还对得上吗

## 你不负责

契约形状（B1）、界面（F1/F2/F3）、脱敏与权限（B3——虽然代码在你这边，
但**判定归 B3**，你发现了就抄送）。

## E1 · 错误处理

项目规矩：**生产代码不用 `unwrap` / `expect` / `panic`**（测试豁免）。

```bash
grep -rn "\.unwrap()\|\.expect(\|panic!\|unreachable!\|todo!" crates/*/src/*.rs
```

当前生产代码里是 **0 处**。你的任务是确认：

1. 这个 0 是真的（上面的 grep 会不会漏掉多行写法）
2. 那么错误是**怎么处理**的——逐个 `?` 与 `match` 看下去：
   - 有没有 `let _ = ...` 把错误丢掉的（`grep -rn "let _ = " crates/*/src`）
   - 有没有 `.ok()` 把 `Result` 压成 `Option` 之后就不管了
   - 有没有 `unwrap_or_default()` 用在**不该有默认值**的地方
     （比如读配置失败当成空配置）
3. 错误信息够不够定位问题：`anyhow` / 自定义错误里带没带上下文
   （哪个节点、哪个运行、哪个路径）

**重点看这三处**（失败在这里最难查）：

| 位置                  | 看什么                                    |
| --------------------- | ----------------------------------------- |
| `runner.rs`（759 行） | 节点执行失败时，事件里记了什么            |
| `exec.rs`             | 子进程的 stdout/stderr 读取失败怎么办     |
| `worktree.rs`         | git 命令失败时，是不是留下了半个 worktree |

## E2 · 并发与锁

这个引擎的并发模型：**每个运行一个线程 + 一条 SQLite 连接**；
devserver 是**固定大小工作线程池**，每线程一份连接。

逐条核实：

1. **锁的粒度**：`Mutex<Store>` 被握住的最长时间是多久？
   有没有在持锁期间做 I/O（起进程、等 ACP、读文件）？
   `devserver/src/main.rs` 的注释说「共用一个 Mutex<Store> 的话线程池救不了任何东西」——
   确认现在真的不是那样
2. **连接归属**：确认没有跨线程共享 `Connection`
3. **写并发**：SQLite WAL 下多连接并发写会 `SQLITE_BUSY`，
   有没有设 `busy_timeout`？重试策略是什么？
   （压测方法见 `devserver/tests/concurrency_test.rs`）
4. **取消的时机**：`supervisor.rs` 说「取消在节点边界生效」——
   那么正在跑的子进程会被 kill 吗？跑了 10 分钟的脚本呢？
5. **挂在审批上的运行不占执行槽**——去代码里确认这个机制真的存在，
   并想清楚：100 个运行同时挂在审批上会怎样

## E7 · 审批与检查点

1. **审批是引擎强制的暂停点**——确认执行器**无法绕过**：
   去代码里找有没有任何路径能在未获批时继续
2. **每个节点完成后落一次带 Scope 快照的检查点**——
   检查点写入与节点状态更新是不是在**同一个事务**里？
   不是的话，中间崩溃会留下不一致
3. **恢复**：`run.resume` 从事件流算出哪些节点已完成。
   核实它算的是「去重的 succeeded」还是「最后一条事件」——
   重试过的节点（failed 后 succeeded）算不算完成
4. **rewindToApproval**：开的是新运行还是改旧的？
   旧运行的事件流有没有被动过（不该动）
