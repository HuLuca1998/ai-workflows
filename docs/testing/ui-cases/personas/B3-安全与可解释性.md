# 第一副眼镜 · 安全

## S1 · 安全基元的代码审查

先读代码，再去界面上试着绕过。

### PathGuard（`path_guard.rs`）

规矩是「每种绕过方式都要有一条用例」。逐条核对测试里有没有：

| 绕过手法                      | 有测试吗 | 代码里怎么防的 |
| ----------------------------- | -------- | -------------- |
| `../` 相对路径                |          |                |
| 绝对路径                      |          |                |
| **符号链接指向根外**          |          |                |
| 链接的链接（多级）            |          |                |
| 大小写差异（macOS 不区分）    |          |                |
| Unicode 规范化差异（NFC/NFD） |          |                |
| 尾随斜杠、`.`、空路径         |          |                |
| 竞态（检查后被替换成链接）    |          |                |
| 超长路径 / 超深嵌套           |          |                |

**最后一条最容易漏**：先检查路径合法，再打开文件——
两步之间文件可能被换成符号链接（TOCTOU）。代码是怎么处理的？

## S5 · 诊断包不含 Secret

两条路径都测：执行记录 → 失败运行 → 「导出诊断包」；
首次配置 → 「导出脱敏诊断报告」。

```bash

grep -R "keychain://" <导出路径>       # 允许出现引用
```

界面要说清楚它安全：「已导出到 …」+
「· 内容已过脱敏器，Secret 只以 keychain:// 引用出现」。

再确认诊断包里**产物只列元信息不含内容**（承诺如此）。

## S6 · 权限档真的在拦

前置：一条含**脚本节点**的工作流。三档各跑一次：

| 权限档              | 运行后期望                               |
| ------------------- | ---------------------------------------- |
| Review Every Change | 脚本节点**执行前挂起**，状态「等待审批」 |
| Workspace Safe      | 脚本直接执行，不挂审批                   |
| Trusted Workflow    | 记录实际行为                             |

Review Every Change 下**没挂起而是直接跑了** → **严重**：界面承诺了引擎没做。

还要测：

- 选档失败时（断网）界面**退回原值**而不是留假的选中态
- 侧栏显示的档位与设置页一致
- 换档之后，**已经在跑**的运行沿用它启动时的档（不该被中途改变）

## S7 · MCP 写确认

三条安全默认逐条验证：

| 默认         | 怎么验                                                  |
| ------------ | ------------------------------------------------------- |
| 出错不放行   | 决定请求失败（断网）时卡片**留着**，不能当作已批准      |
| 超时不放行   | 弹出后**不理它**，等 180 秒，MCP 侧应收到「拒绝」       |
| 只能决定一次 | 「批准」连点 5 次只生效一次；决定后卡片消失且不可再决定 |

制造待确认：


文案一字不差、批准后写入**真的发生**、拒绝后**没有发生**。

再确认 `mcp.pendingConfirms` 与 `mcp.decideConfirm` **不在**远端可调用的
工具清单里（给远端就等于让 MCP 自己批准自己）。

# 第二副眼镜 · 可解释性

## V1 · 首页状态列 = 最近一次运行

| 检查                   | 方法                                       |
| ---------------------- | ------------------------------------------ |
| 状态徽章文案           | 与执行记录里那条运行一致                   |
| 「最近一次运行」的时间 | 与详情头部一致                             |
| 时长                   | 自己算 `endedAt - startedAt`               |
| 失败时的「· 节点 N」   | 与实际失败节点一致                         |
| 版本 Tag               | **与那次运行引用的版本一致，不是最新版本** |
| 从未运行过             | 「已创建」+「未运行」                      |
| 只有草稿               | 版本列是「草稿」                           |

**重点**：发布 v1 → 运行 → 发布 v2 → 发布 v3 → 首页版本列应显示 **v1**
（跟着最近一次运行走）。

## V2 · 统计卡

等待审批 / 今日运行 / Token 用量（应显示「—」不是 0）/ 活跃 worktree，
逐个与列表实际数量核对。跨零点时再看一次「今日运行」。

## V3 · 事件流完整性

1. **seq 连续无缺口**（用 `/ipc/run_events` 拉一份对照界面）
2. 生命周期齐全：`run.started` 开头、终态结尾
3. 每个节点 started/succeeded 配对
4. 右上角「N 条事件」= 实际条数
5. **超过 200 条时全部拉完**：找一条 217 条事件的运行，界面应显示 217 不是 200
6. 超过 5000 条时应有「还有更多没显示」的提示，不能静默截断

## V4 · 节点进度 = 事件流

节点顺序、状态、「N 个节点已完成」（数 `node.succeeded` 的**去重节点数**）、
重试成功的节点最终应显示「完成」、显示的是标题不是 nodeId。

**改名测试**：跑完一次 → 回编辑器把节点改名 → 回来看这条运行，
显示的应该还是**跑的时候**那个名字（事件记的是当时的名字）。

## V5 · 进度条

按 `完成节点数 × 10%` 算。**一个 5 节点的工作流全部跑完 → 进度条只有 50%**。
用户会以为还没跑完。记录实际表现并判定。

## V6 · 时间与时长

全应用格式一致（`zh-CN` + 24 小时制）。逐屏核对。

边界：

- 排队中被取消的运行（**没有 startedAt**）→ 不能显示从 1970 年起的时长
- 还在运行中的（没有 endedAt）→ 不能显示负数
- 跨天运行（>24 小时）→ 记录实际

## V7 · 版本引用

1. 发布 v1 → 运行（runId-A）→ 改草稿 → 发布 v2 → 运行（runId-B）→ 再改草稿
2. 核：A 引用 v1 且 v1 的图没变；B 引用 v2；
   版本抽屉的 Diff 方向是「选中版本 → 当前草稿」；
   回滚到 v1 后 **v2 仍在版本列表里**；回滚不删除任何版本
3. **用草稿跑**的运行：引用的是 rev 而不是版本号，之后改草稿不影响这条记录

## V8 · 刷新与多标签一致

执行记录选中一条后刷新 / `?run=X` 刷新 / 两个标签页看同一条运行 /
一页批准另一页跟上 / 编辑器改了没保存后刷新（beforeunload）/
编辑器改了没保存站内跳走再回来（**改动仍在**）。

## V9 · 空值显示规则

原则是「缺席时显示『—』而不是 0」。逐处核：Token 用量、环境版本列、
模型延迟（「尚未测试」）、Agent 降级模型（「不降级」）、
提示词输出契约（「未声明」）、节点凭据（「未设置」）。

**每一屏都跑一次这段**：

```js
const 坏值 = /undefined|null|NaN|Invalid Date|\[object Object\]/;
[...document.querySelectorAll('main *, aside *')]
  .filter((el) => el.children.length === 0 && 坏值.test(el.textContent))
  .forEach((el) => console.error('[坏值]', el.textContent, el));
```

任何 `undefined` / `NaN` / `Invalid Date` → 缺陷。

## V10 · 计数一致性

首页「N 个工作流」= 分页「共 N 条」/ 「并行进行中 · N」/「历史 · N」/
「N 条事件」/ 记忆「N 条」/ 分组计数 / 编辑器「N 节点 N 连接」/
「已选 N 个」/ 环境「N 项待处理」/ 首次配置「确认并安装（N 项）」。

**筛选/搜索之后每一个计数都要重新核**——最常见的 bug 是总数没跟着筛选变。

## V11 · 界面说的话 vs 实际行为

逐条验证，不成立即**严重**级（界面承诺了却不存在，比没这句话更糟）：

| 界面上的话                                   | 怎么验                                    |
| -------------------------------------------- | ----------------------------------------- |
| 「改动只影响草稿」                           | 改完保存，已发布版本的图不变              |
| 「发布快照不可变」                           | 发布后改草稿，版本图不变                  |
| 「每次运行一个独立目录，并行运行互不影响」   | 同时跑两条，工作目录不同，互不干扰        |
| 「系统内所有模型下拉只列出这里已启用的条目」 | 停用一个模型，去 Agent 页看下拉里还有没有 |
| 「节点引用角色而不是复制 Prompt」            | 改 Agent 保存新版本，引用它的节点跟着变   |
| 「内置角色不能删除」                         | 内置条目没有删除按钮                      |
| 「内置提示词不能直接改」                     | 只读展示，保存时报错并提示先复制          |
| 「记忆会注入后续每一次 AI 调用」             | 运行时有 `system.memory_injected` 事件    |
| 「删除后不再注入」                           | 删掉再跑，事件里不带它                    |
| 「停用则先留着不生效」                       | 停用后仍在列表，但不注入                  |
| 「批准过的节点恢复运行时不再重复询问」       | 批准 → 中断 → 恢复，不再问同一个          |
| 「重试成功的不重跑」                         | 重试后已成功节点没有新的 started 事件     |
| 「用相同参数重跑是一次全新的运行」           | 产生新 runId，原记录还在                  |
| 「杀掉 App 后重启回到同一审批点」            | 真杀进程再起，验证                        |

最后一条是 M2 的出口标准，**必须真的杀进程验证**，不能只看测试。
