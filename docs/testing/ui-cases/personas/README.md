# 审查小队 · 六个角色

一个人看一个系统，看到的永远是他自己关心的那一类问题。
这里把审查拆成六个**视角互斥**的角色：前端三个、后端三个。

每个角色都做两件事——**跑界面**和**读代码**。只跑不读会漏掉「碰巧没触发」的问题，
只读不跑会漏掉「代码看着对但用起来不对」的问题。这个产品两种都栽过。

执行者是 codex。**一次只扮演一个角色**，把那份剧本从头跑完。
「顺手把别的也看了」正是漏检的开始。

## 分工边界（防止六份报告写同一件事）

同一个现象只该被记录一次。判断归谁，看**它最先违背了哪条承诺**：

| 现象                                       | 归谁 |
| ------------------------------------------ | ---- |
| 间距/颜色/层级不对，一屏没有重点           | F1   |
| 图纸有而实现没有的元素或交互               | F1   |
| 功能存在但用户找不到入口（翻页藏太深）     | F1   |
| 想点但点不动、点了给的不是想要的           | F1   |
| 拖动掉帧、列表卡顿、点了没中间态           | F2   |
| 断网/后端挂/超长输入/并发冲突的表现        | F2   |
| 只能用鼠标完成的操作、焦点丢失、读屏念不出 | F2   |
| 前端代码重复、命名、类型、副作用、可读性   | F3   |
| 契约与生成物漂移、DTO 形状不一致、错误码   | B1   |
| Rust 正确性、并发、锁、事务、迁移          | B2   |
| 明文 Secret、权限档没生效、路径逃逸        | B3   |
| 界面显示与引擎事实不一致                   | B3   |

**升级规则**：任何人发现「明文 Secret 外泄」「数据丢失」「界面白屏」，
立刻停下，按最高严重度记录，报告首行标 `⚠️ 阻塞`，并抄送 B3。

## 执行顺序

推荐这个顺序，因为后面的角色能用到前面的产出：

```
F3（前端代码审查）→ B1（契约）→ B2（引擎）    ← 静态，不需要环境
        ↓
F1（界面与体验）→ F2（交互健壮性）→ B3（安全与可解释性）  ← 动态，需要跑起来
```

理由：先读代码的三个角色会产出「可疑清单」（哪里可能不一致、
哪里没有测试覆盖），跑界面的三个角色带着这份清单去验证，效率高得多。

F2 会故意把数据搞坏，**跑完必须重建数据库**再交给 B3。

## 环境

```bash
rm -rf /tmp/aiwf-ui-test
pnpm dev:server -- --port 5177 --db /tmp/aiwf-ui-test/aiwf.sqlite   # 终端 1
pnpm dev:full                                                        # 终端 2
```

只读代码的角色（F3/B1/B2）不需要起环境，但**必须能跑门禁**：

```bash
pnpm verify          # 完整门禁，等价于 CI
pnpm test            # 只跑 TS 测试
pnpm rs:test         # 只跑 Rust 测试
pnpm contracts:check # 契约生成物是否漂移
pnpm lint            # oxlint
pnpm typecheck
```

## 代码审查的共同纪律

三个审查角色（F3/B1/B2，以及 B3 的代码部分）都遵守下面这几条。

### 一、先跑门禁，再动脑子

门禁已经在管的事情不要重复人工审：格式（prettier）、lint 规则、类型错误。
**你的价值在门禁管不到的地方**：重复、命名、抽象层次、可读性、
测试是否真的在测东西、注释是不是在复述代码。

跑一遍 `pnpm verify`，把结果贴进报告。**门禁不绿的话先报这个，别的都往后放。**

### 二、这个项目的硬规矩（违反即缺陷，不是建议）

| 规矩                                                                            | 出处       |
| ------------------------------------------------------------------------------- | ---------- |
| 注释与文档用中文，标识符用英文                                                  | CLAUDE.md  |
| 注释解释「为什么」，不复述「是什么」                                            | CLAUDE.md  |
| Rust：`unsafe` 禁用；生产代码不用 `unwrap`/`expect`/`panic`                     | CLAUDE.md  |
| TS：`strict` + `noUncheckedIndexedAccess` + `exactOptionalPropertyTypes` 不许关 | CLAUDE.md  |
| Secret 只进 Keychain，别处一律 `keychain://` 引用                               | CLAUDE.md  |
| 业务代码只用 `var(--…)`，不写死 hex / px / 字体                                 | tokens.css |
| 契约生成物不许手改                                                              | CLAUDE.md  |
| 新增节点类型不该改 UI 代码（Schema 驱动）                                       | CLAUDE.md  |
| 不为某个视图新建状态表；RunEvent 是唯一事实来源                                 | CLAUDE.md  |
| 测试先行：契约每个导出、安全基元每种绕过、每个修过的坑                          | TESTING.md |

### 三、缺陷要能被复现或定位

每条缺陷必须给到 `文件:行号`，并写清**它会怎么坏**——
「这样写不好」不算缺陷描述，「输入 X 时会得到 Y，而应该是 Z」才算。

### 四、区分「缺陷」与「建议」

- **缺陷**：违反上表的硬规矩、功能错误、数据不一致、安全问题、
  图纸偏离 → 可以直接修
- **建议**：风格偏好、架构重构、图纸没规定的改进 →
  单独一节，标注「需确认」，**不得据此直接改 UI**

这个项目的第一纪律是「UI 严格按图纸施工」。把建议混进缺陷里，
会导致有人照着改，然后 UI 偏离图纸被推翻重做。

## 每个角色的产出

```
docs/testing/evidence/round-<N>/<代号>/
├── report.md            结论报告
├── shots/               截图（跑界面的角色必须有）
├── console.log          控制台输出
└── metrics.json         F2 必须：帧率、长任务、响应时长原始采样
```

报告模板：

```markdown
# <代号> <角色名> · 第 N 轮

- 日期 / 提交 hash / 形态 / 窗口尺寸 / 浏览器版本
- 门禁结果：pnpm verify 是否全绿（不绿的贴失败项）
- 覆盖：看了哪些屏 / 哪些文件，哪些没看及原因
```
