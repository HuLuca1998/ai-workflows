# 17 · MCP 写确认

一张会在**任何一屏**弹出来的确认卡（它挂在应用最外层）。

背景：「AI 的改动一律先出 Diff，用户确认才落草稿」是这个产品的核心规则。
主管 AI 遵守了；MCP 之前不能——那个进程弹不出应用里的对话框，
于是写工具只能整体关掉。

现在它把待确认放进**跨进程信箱**（`mcp_confirmation` 表），
应用轮询到之后显示这张卡，用户决定后 MCP 那边的轮询读到结果。
**写工具因此默认开放了，但每一次写都要人点头。**

三条安全默认：**出错不放行、超时（180 秒）不放行、决定只能做一次**。

> 这张卡**不在图纸里**：图纸画的是 M1 的形态，那时 MCP 还没有写工具。
> 所以 F1 的图纸稽核不适用于它。

## 元素清单

| #   | 元素             | 内容                                                                                                 | 能点吗     |
| --- | ---------------- | ---------------------------------------------------------------------------------------------------- | ---------- |
| 1   | 卡片             | `role="alertdialog"`，`aria-label="MCP 写入确认"`                                                    | —          |
| 2   | 标题             | 插头图标 + 「MCP 客户端要写入：`<工具名>`」                                                          | 纯展示     |
| 3   | 入参             | 格式化后的 JSON（坏 JSON 时原样显示）                                                                | **待验证** |
| 4   | 说明             | 「批准后这次写入会走 Core API 的版本守卫与审计，改的是草稿而不是已发布版本。不理它的话会自动拒绝。」 | 纯展示     |
| 5   | 「拒绝」         | —                                                                                                    | 应可点     |
| 6   | 「批准这次写入」 | 主按钮                                                                                               | 应可点     |

## 怎么造一次待确认

真实路径：用 MCP 客户端调一个写工具（见 `docs/MCP.md`）。

快速路径：

```bash
curl -s -XPOST http://127.0.0.1:5177/ipc/mcp_request_confirm \
  -H 'content-type: application/json' \
  -d '{"tool":"workflow.create","inputJson":"{\"name\":\"来自 MCP\"}"}'
```

轮询间隔 1200ms，所以最多等 2 秒卡片就会出现。

## 用例

### MCP-01 · 卡片在任何一屏都会弹

- 类型：功能
- 操作：分别停在这五屏，各造一次待确认：
  概览 / 编辑器 / 执行记录 / 记忆 / 设置
- 预期：
  1. 五屏都在 2 秒内弹出卡片
  2. 卡片**不把当前屏挡死**（还能看到自己在干什么）
  3. `role="alertdialog"` —— 读屏会播报
- 失败判定：只在某些屏出现（那用户会在不知情的情况下让它超时）

### MCP-02 · 入参原样摊开

- 类型：功能 / 安全
- 操作：造一次带复杂入参的确认：

  ```bash
  curl -s -XPOST http://127.0.0.1:5177/ipc/mcp_request_confirm \
    -H 'content-type: application/json' \
    -d '{"tool":"workflow.patch","inputJson":"{\"id\":\"wf_1\",\"baseRevision\":3,\"operations\":[{\"op\":\"removeNode\",\"nodeId\":\"entry\"}]}"}'
  ```

- 预期：
  1. 入参**格式化**显示（缩进的 JSON），不是一行挤在一起
  2. 用户能看清它到底要改什么（这个例子里是**删掉入口节点**）
  3. 不只给一个工具名就让人决定
- 失败判定：只显示工具名；或 JSON 挤成一行看不清

### MCP-03 · 坏 JSON 的入参

- 类型：边界
- 操作：`inputJson` 传一段不能解析的文本
- 预期：**原样显示**（那本身也是有用的信息），不崩溃
- 失败判定：卡片白屏或不显示

### MCP-04 · 批准

- 类型：功能
- 操作：造一次 `workflow.create` 的确认 → 点「批准这次写入」
- 预期：
  1. 卡片消失
  2. **那条写入真的发生了**——去 `/` 看列表里多了一条「来自 MCP」
  3. MCP 侧（如果用真实客户端）收到成功返回与真实 id
- 失败判定：批准了但列表里没有

### MCP-05 · 拒绝

- 类型：功能 / 安全
- 操作：再造一次 → 点「拒绝」
- 预期：
  1. 卡片消失
  2. **那条写入没有发生**（列表里没有多）
  3. MCP 侧收到拒绝
- 失败判定：拒绝了还是写进去了（**阻塞级**）

### MCP-06 · 决定只能做一次

- 类型：边界 / 安全
- 操作：100ms 间隔连点「批准这次写入」5 次
- 预期：
  1. 按钮在处理期间**禁用**
  2. 只生效一次（列表里只多一条）
  3. 不出现报错刷屏
- 失败判定：建出多条

### MCP-07 · 超时不放行

- 类型：安全（**核心默认**）
- 操作：造一次确认，**什么都不点**，等 180 秒
- 预期：
  1. 到时之后 MCP 侧收到的是**拒绝**
  2. 界面上的卡片消失（或变成已过期）
  3. 那条写入**没有发生**
- 说明：一条写操作在几小时后突然生效，比它没生效糟得多。
- 失败判定：超时后仍然放行；或卡片永远挂着

### MCP-08 · 出错不放行

- 类型：安全（**核心默认**）
- 操作：
  1. 造一次确认
  2. 断网
  3. 点「批准这次写入」
- 预期：
  1. 决定发不出去
  2. **卡片留着**，用户能再按一次
  3. 不能当作已批准
- 说明：静默消失的话他会以为已经批准了。
- 失败判定：卡片消失了（用户以为批准成功，实际什么都没发生）

### MCP-09 · 多条待确认排队

- 类型：边界
- 操作：连续造三次确认
- 预期：**记录实际行为**——当前实现只显示 `items[0]`（第一条）。
  处理完第一条后，第二条会在下一次轮询（≤1.2 秒）出现吗？
- 检查：
  1. 三条能不能依次处理完
  2. 用户知不知道后面还排着两条（有没有计数）
- 判定：没有任何「还有 N 条」的提示 → 记进建议
  （用户以为处理完了，其实还有）

### MCP-10 · 轮询开销

- 类型：性能
- 操作：不造任何确认，在任意屏停留 2 分钟，看网络面板
- 预期：
  1. `mcp_pending_confirms` 每 1.2 秒一次，**匀速**
  2. 切屏之后不叠加（不会变成每 1.2 秒两次、三次）
- 失败判定：请求频率随着切屏次数递增（详见
  [F2 剧本 P6](personas/F2-交互健壮性.md)）

### MCP-11 · 轮询失败时不打扰用户

- 类型：边界
- 操作：停掉 devserver，在应用里待着
- 预期：**不出现**任何报错提示
- 说明：这条报错帮不上用户——他此刻在做别的事，而 MCP 那边会自己超时。
- 失败判定：满屏错误提示

### MCP-12 · 批准的写入真的走了版本守卫

- 类型：安全 / 可解释性
- 操作：
  1. 打开某条工作流的编辑器，记下当前 rev（比如 5）
  2. 在编辑器里改一下并保存（rev 变成 6）
  3. 造一次 `workflow.patch` 的确认，`baseRevision` 填 **5**（过期的）
  4. 批准它
- 预期：
  1. 写入**被版本守卫拒绝**（baseRevision 过期）
  2. MCP 侧收到冲突错误
  3. 草稿没有被改坏
- 说明：卡片的说明里承诺了「会走 Core API 的版本守卫与审计」——
  这条就是验证它。
- 失败判定：过期的 baseRevision 也写进去了（守卫形同虚设）

### MCP-13 · 改的是草稿不是已发布版本

- 类型：安全
- 操作：对一条已发布 v1 的工作流，批准一次 MCP 的 patch
- 预期：
  1. 草稿变了
  2. **v1 的图没有变**
- 失败判定：已发布版本被改（**阻塞级**，那意味着快照不再不可变）

### MCP-14 · 确认接口不给远端

- 类型：安全
- 操作：连上 MCP Server，列出它暴露的工具
- 预期：`mcp.pendingConfirms` 与 `mcp.decideConfirm` **不在列表里**
- 说明：给远端就等于让 MCP 自己批准自己。它们的 Scope 是 null。
- 失败判定：出现在工具清单里（**阻塞级**）

### MCP-15 · 读屏能不能感知到它

- 类型：无障碍
- 操作：开着读屏，造一次确认
- 预期：卡片弹出时**被播报**（`role="alertdialog"`）
- 说明：它是打断性的。读屏用户听不到就会在不知情的情况下让它超时（超时＝拒绝）。
- 失败判定：无声出现

### MCP-16 · 卡片的键盘可达性

- 类型：无障碍
- 操作：不用鼠标，用键盘处理一次确认
- 预期：
  1. 焦点能到达两个按钮
  2. 回车能触发
  3. **Esc 不该关掉它**（关掉等于什么都没决定，而它需要一个明确的决定）
- 判定：Esc 能关掉的话，记录关掉之后发生了什么——
  是当作拒绝，还是卡片消失但请求还挂着？后者是缺陷。

### MCP-17 · 三问清点

- 类型：体验
- 操作：对这些做三问：
  工具名（想知道这个工具是干什么的）、
  入参 JSON（想复制它、想展开/折叠）、
  说明里的「版本守卫与审计」（想知道审计记录在哪看）
- 重点：
  1. **入参很长时怎么办**？一个 patch 可能有几十个操作——
     卡片会被撑多高？能滚动吗？
  2. **用户怎么判断这次写入安不安全**？工具名 + 入参够吗？
     有没有办法看到「这是哪个 MCP 客户端发来的」
