# 09 · 审批与失败恢复

这一屏是执行记录详情区里的两块：**审批面板**（等待审批时出现）与
**失败横幅**（有节点失败时出现）。加上编辑器顶部的审批横幅。

核心承诺：**审批是引擎强制的暂停点**（执行器无法绕过）、
**失败可从失败节点重试**（成功的不重跑）。

## 前置：怎么造出这些状态

| 需要的状态 | 怎么造                                                               |
| ---------- | -------------------------------------------------------------------- |
| 等待审批   | 权限档设成 `review_every_change`（默认档），跑一条含脚本节点的工作流 |
| 失败       | 脚本节点写 `exit 1`                                                  |
| 超时失败   | 脚本写 `sleep 60`，超时设成 5 秒                                     |
| 多次尝试   | 节点的重试次数设成 2，脚本必失败                                     |

## 用例

### APR-01 · 默认权限档下脚本节点会挂起

- 类型：功能 / 安全（**核心承诺**）
- 前置：权限档是 `review_every_change`（全新库的默认值）
- 操作：跑一条含脚本节点的工作流
- 预期：
  1. 运行状态变成「等待审批」
  2. 详情区出现审批面板
  3. 节点进度里那个节点显示「待审批」（手掌图标）
  4. **脚本还没有执行**（去工作目录确认它没产生文件）
- 失败判定：脚本直接跑了——界面上的权限档就是假的安全感
  （**严重，抄送 [B3 剧本 S6](personas/B3-安全与可解释性.md)**）

### APR-02 · 批准后继续执行

- 类型：功能
- 操作：点「批准」
- 预期：
  1. 审批面板消失
  2. 运行状态回到「运行中」
  3. 那个节点开始执行，最终变成「完成」
  4. 事件流里有 `approval.requested` 与 `approval.decided` 两条
  5. 决定被记录（谁批的、什么时候）
- 失败判定：批准了但运行没继续

### APR-03 · 拒绝后运行终止

- 类型：功能
- 操作：再跑一次，这次点「拒绝」
- 预期：
  1. 运行进入终态（失败或已取消，记录实际是哪个）
  2. 那个节点**没有执行**
  3. 事件流里能看出是被拒绝的
- 失败判定：拒绝了脚本还是跑了

### APR-04 · 连点「批准」只决定一次

- 类型：边界
- 操作：100ms 间隔连点「批准」5 次
- 预期：只发一次 `approval_decide`，不出现「已被决定」这类报错刷屏
- 失败判定：报错弹了四次

### APR-05 · 审批面板显示的是在批什么

- 类型：可解释性
- 操作：看审批面板的标题
- 预期：显示的是审批请求事件里的**摘要**（在批什么），
  不只是一个节点 id
- 失败判定：显示 `internal_shell_77` 这种用户从没见过的 id

### APR-06 · 两个标签页同时批准

- 类型：边界
- 操作：两个标签页都停在同一条待审批的运行上，同时点「批准」
- 预期：一个成功，另一个得到可理解的错误（「已被决定」之类），
  **不能两个都成功**
- 失败判定：产生两条决定记录

### APR-07 · 杀掉进程后重启回到同一审批点

- 类型：功能（**M2 出口标准**）
- 操作：
  1. 跑到审批点停住
  2. **杀掉 devserver 进程**（Ctrl-C）
  3. 重新起 devserver，刷新页面
  4. 找到那条运行
- 预期：
  1. 它仍然是「等待审批」
  2. 审批面板还在，批准后能继续跑完
  3. **上游节点的输出跨重启存活**（后续节点能拿到它）
- 失败判定：重启后运行丢了、或状态变成失败、或批准后拿不到上游数据

### APR-08 · 批准过的节点恢复时不再重复询问

- 类型：功能
- 操作：接 APR-07，批准后让它继续跑，中途再杀一次进程，重启后恢复
- 预期：**不再问同一个节点**（已批准的决定被记住了）
- 失败判定：又弹一次同样的审批

### FAIL-01 · 失败横幅出现

- 类型：功能
- 前置：一条脚本 `exit 1` 的工作流跑完
- 操作：选中那条失败的运行
- 预期：
  1. 详情区出现失败横幅（`role="alert"`）
  2. 标题是「节点「<节点标题>」失败」——**用标题不是 id**
  3. 右侧显示「attempt N」（只有一次尝试时也照样写出来）
  4. 已结束的运行还显示时长
  5. 下方显示失败详情（失败事件的摘要）
  6. 四个按钮都在
- 失败判定：显示 nodeId；或时长显示成从 1970 年起

### FAIL-02 · 排队中被取消的运行不显示离谱时长

- 类型：边界
- 操作：造一条**还没开始就被取消**的运行（没有 startedAt），选中它
- 预期：不显示时长，或显示为空——**绝不能显示 1970 年起的天数**
- 失败判定：显示「486000m00s」这类数字

### FAIL-03 · 从失败节点重试

- 类型：功能（**M5 出口标准**）
- 前置：一条有 3 个节点的工作流，第 1、2 个成功，第 3 个失败
- 操作：点「从失败节点重试」
- 预期：
  1. 运行恢复执行
  2. **前两个节点不重跑**——事件流里它们没有新的 `node.started`
  3. 第 3 个节点重新执行
  4. 修好脚本后重试能跑完
  5. 这是**同一条运行**（runId 不变）
- 失败判定：整条重跑了（前面几十分钟的工作白费）

### FAIL-04 · 用相同参数重跑

- 类型：功能
- 操作：点「用相同参数重跑」
- 预期：
  1. 产生一条**新的运行**（新 runId）
  2. 参数与原来相同
  3. **原来那条仍在列表里**，两条可以对照着看
  4. 界面自动选中新的那条
  5. 用的是原运行引用的**同一个版本**（不是当前草稿——
     草稿可能已经改过，那就不是「相同」重跑了）
- 失败判定：覆盖了原来那条；或跑的是当前草稿

### FAIL-05 · 回到最近审批点改选择

- 类型：功能
- 前置：一条「审批 → 批准 → 后续节点失败」的运行
- 操作：点「回到最近审批点改选择」
- 预期：
  1. 开的是**新运行**，原来那条留着
  2. 新运行停在那个审批点，等你重新决定
  3. 审批之前已完成的工作被保留（不是从头跑）
  4. 界面自动选中新的那条
- 失败判定：动了原来那条运行的事件流

### FAIL-06 · 三个恢复按钮的区别用户分得清吗

- 类型：体验
- 操作：把三个按钮的文案与 hover 提示念一遍
- 预期：能回答「什么时候用哪个」
- 说明：这三个的差别很微妙：
  - 从失败节点重试 = 同一条运行，成功的不重跑
  - 回到最近审批点 = 新运行，回到那个决定之前
  - 用相同参数重跑 = 新运行，从头
    界面上有没有说清？没有的话记进**建议**（图纸只给了按钮文案）。

### FAIL-07 · 导出诊断包

- 类型：功能 / 安全
- 操作：点「导出诊断包」
- 预期：
  1. 成功后显示「已导出到 <路径>」（`role="status"`）
  2. 后面跟着「· 内容已过脱敏器，Secret 只以 keychain:// 引用出现」
  3. 路径是真实存在的文件
  4. 失败时显示错误而不是静默
- 失败判定：只说「已导出」不给路径（用户找不到它）

### FAIL-08 · 诊断包不含 Secret

- 类型：安全
- 操作：见 [B3 剧本 S5](personas/B3-安全与可解释性.md)
- 预期：`grep TESTLEAK` 无结果

### FAIL-09 · 失败详情够不够用

- 类型：体验 / 可解释性
- 操作：看失败详情那段文字，问自己：**够判断问题吗**
- 检查：
  1. 有没有退出码
  2. 有没有 stderr 的内容
  3. 内容被截断了吗？截断了有没有说「完整日志见产物」
  4. **能不能复制**这段文字
  5. 想看完整日志的话，从这里点得过去吗
- 说明：图纸这里有一个等宽字体的错误块，写着
  `exitCode 124 · killed after 30s` 与 `stderr: …（已截断，完整日志见产物）`，
  还有「错误分类：timeout」。
  当前实现只有摘要——差异复核见 [F1 剧本 B4](personas/F1-界面与体验.md) #10。

### FAIL-10 · 重试后失败横幅消失

- 类型：功能
- 操作：修好脚本 → 「从失败节点重试」→ 跑成功
- 预期：
  1. 失败横幅消失
  2. 状态徽章变成「成功」
  3. 节点进度里那个节点从「失败」变成「完成」
- 失败判定：重试成功了横幅还在

### FAIL-11 · 首页的失败行尾图标

- 类型：功能
- 操作：回 `/`，找那条失败的工作流，点行尾的重试图标
- 预期：跳到 `/runs/<那次运行的 id>`
- 说明：注意这里跳的是 `/runs/<id>` 而不是 `/runs?run=<id>`——
  **验证这个路由能不能正确展开那条运行**，不能的话是缺陷。

### FAIL-12 · 三问清点

- 类型：体验
- 操作：对这些做三问：
  失败详情文本（#6）、导出路径（#11，想点它打开所在目录）、
  「attempt 2」（想知道另一次尝试发生了什么）
- 重点：**失败详情**。用户看到「解析失败」的下一个动作一定是
  「让我看完整日志」。从这里有没有一条通往产物或完整日志的路？
