# UI 操作测试总纲

这套文档给**执行测试的人或 AI** 用。每一条用例都是「用鼠标 / 键盘做一件事，
然后看界面变成什么样」——不允许用调用 API、读数据库、看源码的方式代替观察界面。

## 0. 怎么用这套文档

1. 按 §4 的顺序，一个文件一个文件跑。文件内的用例编号是有序的，前一条常常是后一条的前置。
2. 每条用例只有三种结论：**PASS**（预期全部成立）、**FAIL**（任一条预期不成立）、
   **BLOCKED**（前置条件无法建立）。不允许「基本通过」。
3. FAIL 时按 §6 的模板记录，**必须带截图**与当时的控制台 / 网络记录。
4. 不要因为「看起来像小问题」就跳过记录。文案不一致、按钮点了没反应、
   空态说的话与实际不符，都是这个产品的核心缺陷类型（它卖的就是「可解释」）。

## 1. 被测形态

| 形态     | 怎么起                             | 说明                           |
| -------- | ---------------------------------- | ------------------------------ |
| Web 形态 | 浏览器打开 `http://localhost:5173` | 主要测试形态，能用 DevTools    |
| 桌面形态 | `pnpm --filter @aiwf/desktop dev`  | 只跑 §4 标了「桌面必测」的用例 |

**没有连引擎的 Web 形态不能用来测试**：不设 `VITE_AIWF_SERVER` 时前端走内存传输，
列表永远是空的，绝大多数用例会假性通过（看到空态就以为对了）。

## 2. 环境准备

```bash
# 终端 1 —— 真实引擎的 HTTP 桥（桌面版跑的是同一套 core-api）
pnpm dev:server -- --port 5177 --db /tmp/aiwf-ui-test/aiwf.sqlite

# 终端 2 —— Web 界面（等价于 VITE_AIWF_SERVER=http://127.0.0.1:5177 pnpm dev）
pnpm dev:full
```

看到 devserver 打印「aiwf devserver 已启动」并列出命令数，才算起来了。

**每一轮完整测试前重建数据库**（避免上一轮的残留把空态用例挡掉）：

```bash
rm -rf /tmp/aiwf-ui-test && pnpm dev:server -- --port 5177 --db /tmp/aiwf-ui-test/aiwf.sqlite
```

浏览器窗口固定 **1440×900** 开始（基准窗口）。需要改窗口宽度的用例会写明。

### 2.1 数据准备的规矩

**能从界面建的数据，一律从界面建**——那本身就是被测行为。

只有三类状态从界面建不出来或代价过高，允许用 HTTP 调 devserver 铺：

| 需要的状态     | 命令                                                                        |
| -------------- | --------------------------------------------------------------------------- |
| 放宽权限档     | `POST /ipc/workspace_update_settings {"permissionPreset":"workspace_safe"}` |
| 大批量列表数据 | 循环 `POST /ipc/workflow_create {"name":"批量 N"}`                          |
| 造一条失败运行 | 建一个脚本节点写 `exit 1` 的工作流再运行（这条仍走界面）                    |

例：

```bash
curl -s -XPOST http://127.0.0.1:5177/ipc/workspace_update_settings \
  -H 'content-type: application/json' -d '{"permissionPreset":"workspace_safe"}'
```

铺完数据后**刷新页面**再开始用例。

### 2.2 默认权限档会拦住脚本

新库的权限档是 `review_every_change`：脚本、worktree、commit、PR、MCP 工具节点
在执行前会挂起等审批。这是**有意的默认**，不是缺陷。

- 测「审批流」时保持默认档。
- 测「跑到结束」时先把档位改成 `workspace_safe`（界面路径：设置与环境 → 运行环境与工具 → 权限策略 → Workspace Safe）。

## 3. 元素定位约定

给自动化执行的 AI：**优先用无障碍名与可见文本定位**，不要用 CSS class 链
（class 是设计系统的，改样式就会断）。

| 优先级 | 方式              | 例子                                          |
| ------ | ----------------- | --------------------------------------------- |
| 1      | `role` + 可访问名 | `getByRole('button', { name: '新建工作流' })` |
| 2      | `aria-label`      | `[aria-label="搜索工作流"]`                   |
| 3      | 可见文本          | `text=从失败节点重试`                         |
| 4      | `data-*` 状态属性 | `[data-status="failed"]`、`[data-selected]`   |
| 5      | class（最后手段） | `.wf-node`、`.runs__item`                     |

已经稳定可用的 `data-*` 钩子：

- 工作流行：`tr[data-workflow-id]`、`tr[data-clickable="true"]`
- 运行条目：`.runs__item[data-status="succeeded|failed|waiting_approval|running"]`
- 画布节点：`.wf-node[data-tone][data-selected][data-issue]`
- 环境检查行：`[data-capability][data-status]`
- 侧栏：`nav[aria-label="主导航"][data-collapsed="true|false"]`

## 3.5 用浏览器工具怎么执行

执行者是 AI 时，用浏览器自动化工具**真的打开页面点**，不要靠读代码推断结果。

### 3.5.1 起手式

```
1. 打开一个新标签页 → http://localhost:5173
2. 把窗口调到 1440×900
3. 截一张全页截图，作为这一模块的基线
4. 清空控制台，之后每条用例结束都读一次控制台
```

对应工具：`tabs_create_mcp` → `navigate` → `resize_window` → `computer(screenshot)` →
`read_console_messages`。Playwright 则是 `page.goto` / `setViewportSize` /
`screenshot` / `page.on('console')`。

### 3.5.2 每条用例的标准动作

| 动作       | 怎么做                                                           |
| ---------- | ---------------------------------------------------------------- |
| 点击       | 先截图确认元素在视口内且未被遮挡，再点，再截图对比               |
| 输入       | 逐字输入（不要一次性 setValue），中文用输入法文本直接填          |
| 拖放       | 按下 → 分 10 步以上移动 → 松开，全程采帧率（见 3.5.4）           |
| 右键       | 用真实 contextmenu 事件，不要直接调函数                          |
| 键盘快捷键 | 焦点先放在页面主体（点一下空白），再按键                         |
| 等待       | 等界面出现预期文字，不要死等固定秒数；超过 10 秒判定为「无反馈」 |

**每条用例至少留两张截图**：操作前、操作后。FAIL 的必须再加一张标出问题位置的截图。

### 3.5.3 「看得见吗」怎么判定（可发现性）

用户举过的例子就是这一类：_工作流列表要往下滚很远才看得到翻页_。
这类问题必须量化，不能凭感觉。在页面控制台跑：

```js
// 某个元素相对首屏的位置。返回值 > 0 表示要滚动才能看到
(() => {
  const el = document.querySelector('.pager') ?? document.querySelector('[aria-label="分页"]');
  if (!el) return '元素不存在';
  const r = el.getBoundingClientRect();
  return {
    距首屏底部还有: Math.round(r.top - window.innerHeight),
    需要滚动的像素: Math.max(0, Math.round(r.top - window.innerHeight + r.height)),
    页面总高: document.documentElement.scrollHeight,
    视口高: window.innerHeight,
  };
})();
```

判据：

| 结果                      | 结论                                           |
| ------------------------- | ---------------------------------------------- |
| 需要滚动 0 px             | PASS，首屏可见                                 |
| 需要滚动 ≤ 1 屏（≤900px） | PASS，但在报告里记一条「可发现性偏弱」         |
| 需要滚动 > 1 屏           | **FAIL**：主要操作入口不该藏在一屏之外         |
| 元素不存在                | 按该用例的预期判定（有的场景本来就不显示分页） |

同一套方法用于：分页控件、「清除筛选」链接、失败横幅的四个恢复按钮、
启动表单的「开始运行」、版本抽屉底部三个按钮、首次配置底部三个按钮。

### 3.5.4 「卡不卡」怎么判定（流畅度）

拖节点、缩放画布、滚长列表时采帧率。操作**开始前**在控制台起采样：

```js
// 采 3 秒帧率，期间去做拖动 / 滚动操作
window.__fps = (() => {
  const t = [];
  let stop = false;
  const tick = (now) => {
    t.push(now);
    if (!stop) requestAnimationFrame(tick);
  };
  requestAnimationFrame(tick);
  setTimeout(() => {
    stop = true;
    const d = t.slice(1).map((x, i) => x - t[i]);
    const 平均 = d.reduce((a, b) => a + b, 0) / d.length;
    const 长帧 = d.filter((x) => x > 33).length;
    console.log('[FPS]', {
      平均帧率: Math.round(1000 / 平均),
      最长帧ms: Math.round(Math.max(...d)),
      掉帧数: 长帧,
      掉帧占比: `${Math.round((长帧 / d.length) * 100)}%`,
    });
  }, 3000);
})();
```

判据（1440×900、Chrome、非无头）：

| 指标              | PASS    | 记一条体验问题 | FAIL     |
| ----------------- | ------- | -------------- | -------- |
| 平均帧率          | ≥ 55    | 40–54          | < 40     |
| 最长单帧          | ≤ 50 ms | 50–120 ms      | > 120 ms |
| 掉帧占比（>33ms） | ≤ 5%    | 5–20%          | > 20%    |

再配一条长任务监测（主线程被卡住的直接证据）：

```js
new PerformanceObserver((list) => {
  for (const e of list.getEntries()) console.warn('[长任务]', Math.round(e.duration), 'ms');
}).observe({ entryTypes: ['longtask'] });
```

> 超过 200ms 的长任务出现在拖动 / 输入 / 切页过程中，一律记为体验缺陷并附上截图。

### 3.5.5 「有反应吗」怎么判定（响应反馈）

点下去到界面有可见变化的时间：

| 时长        | 结论                                                          |
| ----------- | ------------------------------------------------------------- |
| ≤ 100 ms    | PASS                                                          |
| 100–1000 ms | 必须有中间态（按钮 loading / 「正在读取…」/ 骨架），否则 FAIL |
| > 1000 ms   | 必须有中间态**且**能取消或有进度，否则 FAIL                   |
| 无任何变化  | FAIL，记「点了没反应」                                        |

用网络面板佐证：`read_network_requests` 看请求是否真的发出去了、耗时多少、
有没有重复发（例如输入一个字符发一次请求＝防抖失效）。

### 3.5.6 每条用例必须顺带检查的四件事

不写进每条用例的「预期」里，但每条都要看：

1. **控制台**：有没有报错 / 警告（React key、受控组件、未捕获 Promise）
2. **网络**：有没有 4xx / 5xx；有没有同一请求短时间重复发出
3. **布局**：窗口没有横向滚动条；没有文字被截断成「…」而无 title
4. **焦点**：操作后焦点没有丢到 `<body>`（键盘用户会失去位置）

## 5. 用例格式说明

```
### 编号 · 一句话说明这条要证明什么
- 类型：功能 / 体验 / 边界 / 性能 / 无障碍（可多选）
- 前置：跑这条之前世界必须是什么样
- 操作：编号步骤，每步是一个用户动作
- 预期：编号断言，每条必须肉眼可验证
- 失败判定：常见的错误表现，看到就是 FAIL
```

「预期」里凡是带引号的文案，都是**一字不差**的要求。文案不同即 FAIL，
哪怕意思一样——这个产品的文案是设计的一部分。

## 6. 缺陷记录模板

```markdown
### BUG-<模块>-<序号> 标题（一句话说清现象）

- 用例：OVW-07
- 环境：Web / Chrome 141 / 1440×900 / devserver 5177 / 数据库 /tmp/aiwf-ui-test
- 复现步骤：1. … 2. … 3. …
- 实际：（看到了什么，带截图）
- 预期：（用例里写的那条）
- 严重度：阻塞 / 严重 / 一般 / 轻微
- 控制台：（有报错就贴，没有写「无」）
- 网络：（相关请求与响应码，没有写「无」）
```

严重度判定：

| 级别 | 判据                                                  |
| ---- | ----------------------------------------------------- |
| 阻塞 | 主流程走不下去；数据丢失；界面白屏                    |
| 严重 | 功能不可用但有绕行；状态显示与实际不符；权限/脱敏相关 |
| 一般 | 交互别扭、边界处理不当、错误信息说不清                |
| 轻微 | 文案、间距、图标等观感问题                            |

## 7. 已知的实现差异（不要重复报）

下面这些是**当前实现的已知状态**，测到时按「确认是否仍然如此」处理，

| 位置                           | 现状                                                      |

| 桌面形态标题栏交通灯           | 不自绘，由 macOS 画在同一位置（见 `TitleBar.tsx` 注释）   |
