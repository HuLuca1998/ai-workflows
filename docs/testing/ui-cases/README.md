# UI 操作测试总纲

这套文档给**执行测试的人或 AI** 用。每一条用例都是「用鼠标 / 键盘做一件事，
然后看界面变成什么样」——不允许用调用 API、读数据库、看源码的方式代替观察界面。

## 0. 怎么用这套文档

1. 按 §4 的顺序，一个文件一个文件跑。文件内的用例编号是有序的，前一条常常是后一条的前置。
2. 每条用例只有三种结论：**PASS**（预期全部成立）、**FAIL**（任一条预期不成立）、
   **BLOCKED**（前置条件无法建立）。不允许「基本通过」。
3. FAIL 时按 §6 的模板记录，**必须带截图**与当时的控制台 / 网络记录。
4. 不要因为「看起来像小问题」就跳过记录。文案不一致、按钮点了没反应、
   空态说的话与实际不符，都是这个产品的核心缺陷类型（它卖的就是「可解释」）。

## 1. 被测形态

| 形态     | 怎么起                                          | 说明                                       |
| -------- | ----------------------------------------------- | ------------------------------------------ |
| Web 形态 | 浏览器打开 `http://localhost:5173`              | 主要测试形态，能用 DevTools               |
| 桌面形态 | `pnpm --filter @aiwf/desktop dev`               | 只跑 §4 标了「桌面必测」的用例             |

**没有连引擎的 Web 形态不能用来测试**：不设 `VITE_AIWF_SERVER` 时前端走内存传输，
列表永远是空的，绝大多数用例会假性通过（看到空态就以为对了）。

## 2. 环境准备

```bash
# 终端 1 —— 真实引擎的 HTTP 桥（桌面版跑的是同一套 core-api）
pnpm dev:server -- --port 5177 --db /tmp/aiwf-ui-test/aiwf.sqlite

# 终端 2 —— Web 界面（等价于 VITE_AIWF_SERVER=http://127.0.0.1:5177 pnpm dev）
pnpm dev:full
```

看到 devserver 打印「aiwf devserver 已启动」并列出命令数，才算起来了。

**每一轮完整测试前重建数据库**（避免上一轮的残留把空态用例挡掉）：

```bash
rm -rf /tmp/aiwf-ui-test && pnpm dev:server -- --port 5177 --db /tmp/aiwf-ui-test/aiwf.sqlite
```

浏览器窗口固定 **1440×900** 开始（基准窗口）。需要改窗口宽度的用例会写明。

### 2.1 数据准备的规矩

**能从界面建的数据，一律从界面建**——那本身就是被测行为。

只有三类状态从界面建不出来或代价过高，允许用 HTTP 调 devserver 铺：

| 需要的状态       | 命令                                                                  |
| ---------------- | --------------------------------------------------------------------- |
| 放宽权限档       | `POST /ipc/workspace_update_settings {"permissionPreset":"workspace_safe"}` |
| 大批量列表数据   | 循环 `POST /ipc/workflow_create {"name":"批量 N"}`                     |
| 造一条失败运行   | 建一个脚本节点写 `exit 1` 的工作流再运行（这条仍走界面）              |

例：

```bash
curl -s -XPOST http://127.0.0.1:5177/ipc/workspace_update_settings \
  -H 'content-type: application/json' -d '{"permissionPreset":"workspace_safe"}'
```

铺完数据后**刷新页面**再开始用例。

### 2.2 默认权限档会拦住脚本

新库的权限档是 `review_every_change`：脚本、worktree、commit、PR、MCP 工具节点
在执行前会挂起等审批。这是**有意的默认**，不是缺陷。

- 测「审批流」时保持默认档。
- 测「跑到结束」时先把档位改成 `workspace_safe`（界面路径：设置与环境 → 运行环境与工具 → 权限策略 → Workspace Safe）。

## 3. 元素定位约定

给自动化执行的 AI：**优先用无障碍名与可见文本定位**，不要用 CSS class 链
（class 是设计系统的，改样式就会断）。

| 优先级 | 方式                    | 例子                                            |
| ------ | ----------------------- | ----------------------------------------------- |
| 1      | `role` + 可访问名       | `getByRole('button', { name: '新建工作流' })`   |
| 2      | `aria-label`            | `[aria-label="搜索工作流"]`                     |
| 3      | 可见文本                | `text=从失败节点重试`                           |
| 4      | `data-*` 状态属性       | `[data-status="failed"]`、`[data-selected]`     |
| 5      | class（最后手段）       | `.wf-node`、`.runs__item`                       |

已经稳定可用的 `data-*` 钩子：

- 工作流行：`tr[data-workflow-id]`、`tr[data-clickable="true"]`
- 运行条目：`.runs__item[data-status="succeeded|failed|waiting_approval|running"]`
- 画布节点：`.wf-node[data-tone][data-selected][data-issue]`
- 环境检查行：`[data-capability][data-status]`
- 侧栏：`nav[aria-label="主导航"][data-collapsed="true|false"]`

## 5. 用例格式说明

```
### 编号 · 一句话说明这条要证明什么
- 类型：功能 / 体验 / 边界 / 性能 / 无障碍（可多选）
- 前置：跑这条之前世界必须是什么样
- 操作：编号步骤，每步是一个用户动作
- 预期：编号断言，每条必须肉眼可验证
- 失败判定：常见的错误表现，看到就是 FAIL
```

「预期」里凡是带引号的文案，都是**一字不差**的要求。文案不同即 FAIL，
哪怕意思一样——这个产品的文案是设计的一部分。

## 6. 缺陷记录模板

```markdown
### BUG-<模块>-<序号> 标题（一句话说清现象）

- 用例：OVW-07
- 环境：Web / Chrome 141 / 1440×900 / devserver 5177 / 数据库 /tmp/aiwf-ui-test
- 复现步骤：1. … 2. … 3. …
- 实际：（看到了什么，带截图）
- 预期：（用例里写的那条）
- 严重度：阻塞 / 严重 / 一般 / 轻微
- 控制台：（有报错就贴，没有写「无」）
- 网络：（相关请求与响应码，没有写「无」）
```

严重度判定：

| 级别 | 判据                                                       |
| ---- | ---------------------------------------------------------- |
| 阻塞 | 主流程走不下去；数据丢失；界面白屏                        |
| 严重 | 功能不可用但有绕行；状态显示与实际不符；权限/脱敏相关     |
| 一般 | 交互别扭、边界处理不当、错误信息说不清                    |
| 轻微 | 文案、间距、图标等观感问题                                |

## 7. 已知的实现差异（不要重复报）

下面这些是**当前实现的已知状态**，测到时按「确认是否仍然如此」处理，
写进报告的「已知差异复核」一节，不要当成新缺陷：

| 位置                       | 现状                                                                 |
| -------------------------- | -------------------------------------------------------------------- |
| 主导航徽标                 | 外壳传入的计数恒为空，「等待审批 / 运行中」徽标永远不显示           |
| 标题栏「N 个运行中」       | 同上，永远不显示                                                     |
| 编辑器工具栏撤销 / 重做    | 有意保持禁用（快捷键表里标为待实现）                                 |
| 节点配置弹层「测试运行此节点」 | 有意禁用，提示文案写着「M2 阶段接入」                             |
| 设置页 8 档中的 6 档       | 显示「这一档还没有可配置的项。」                                     |
| 桌面形态标题栏交通灯       | 不自绘，由 macOS 画在同一位置（见 `TitleBar.tsx` 注释）             |

但**这几处文案是否已经过期，要单独确认**（执行到对应用例时按用例要求判定）：

- 执行记录「对话」tab 写「要等 AI 节点接上 ACP（M3）」，而 M3 已交付
- 提示词库「预览」tab 写「等 AI 节点接上 ACP 并跑过一次后」
- 节点配置「重试与超时」tab 写「要等引擎（M2）」，而 M2 已交付
