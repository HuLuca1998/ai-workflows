## 缺陷

### D1 · 概览页的分页控件在首屏下方 2665px，要滚 26 下滚轮才看得见

- 严重度：**严重**
- 角色：F1（可发现性）
- 用例：[OVW-17](../../ui-cases/02-概览与工作流首页.md)
- 复现：打开 `/`（库里 2403 条工作流），不滚动，找翻页

实测数据：

| 项                       | 值                    |
| ------------------------ | --------------------- |
| 滚动容器                 | `.overview`           |
| 容器可视高               | 856 px                |
| 容器内容高               | 3521 px               |
| 分页初始位置（距视口顶） | 3499 px               |
| **需要滚动**             | **2665 px ≈ 2.96 屏** |
| **真实滚轮次数**         | **26 下**             |
| 本页行数                 | 50                    |

判据（总纲 §3.5.3）：需要滚动 > 1 屏 → FAIL。这里是 2.96 屏。

**这正是用户原话反馈的那条**：「流程列表页面看不到翻页，需要往下滚动很远才能翻页」。

对比同类屏——执行记录、Agent、提示词、模型的分页**首屏就可见**（需要滚动 0 px），
因为它们的分页固定在左栏底部，而概览页的分页跟着 50 行表格走到了内容最底下。
**同一个应用里两种布局策略**。

- 角色：F1（体验一致性）/ F3（代码层面见其报告）

| 屏         | 输入不回车等 1.5 秒 | 按回车 | 结论             |
| ---------- | ------------------- | ------ | ---------------- |
| 概览       | 发 1 次请求         | 0 次   | 输入即搜         |
| 执行记录   | 发 1 次请求         | 0 次   | 输入即搜         |
| Agent      | 发 1 次请求         | 0 次   | 输入即搜         |
| **提示词** | **0 次**            | 1 次   | **只有回车才搜** |

用户在概览页学会「打字就搜」，到提示词页打字没反应，会以为搜索坏了。

## PASS 的项

### P1 · 画布拖动帧率达标（但 200 节点有一次 121ms 长帧）

用户反馈过「拖动节点有点卡」。实测（每次拖 30 步走 8 字，约 3 秒）：

| 规模     | 平均帧率 | 最长帧     | 掉帧占比 | 判定                            |
| -------- | -------- | ---------- | -------- | ------------------------------- |
| 10 节点  | 74 fps   | 25 ms      | 0%       | PASS                            |
| 50 节点  | 71 fps   | 53 ms      | 2%       | PASS（最长帧超 50ms 阈值）      |
| 200 节点 | 66 fps   | **121 ms** | 2%       | PASS，但最长帧**超 120ms 阈值** |

长列表滚动（概览页 50 行 + 2403 总数）：74 fps，最长 27 ms，掉帧 0%。

**结论**：Chromium 下测不出「卡」。三个可能的解释，这一轮都没能证实：

1. 桌面形态跑的是 **WKWebView**，帧率没测过（`docs/ROADMAP.md` 也写着「WKWebView 侧待补」）——
   用户实际用的是那个形态
2. 200 节点时那一次 121 ms 的长帧（多半是松手落库那一下）
3. 体感「卡」可能来自别处：打开大图的首次渲染、缩放到 35%、框选整体拖

**这条不算 PASS 也不算 FAIL，算「没能复现」**。要定论必须在桌面壳里测。

### P7 · 交叉验证了 B1 的 D3（`supervisor.ask` 声明只读却写库）

B1 从代码里读出这条，我在真实 devserver 上验证：

```
调用前 supervisor_sessions：12 条
POST /ipc/supervisor_ask
调用后 supervisor_sessions：13 条
```

契约 `packages/contracts/src/api.ts:683-685` 声明 `mutates: false` +
`scope: 'workflow:read'`，实际产生了持久化写入。**独立证实，不是读代码推断。**

（有意思的是：被问到「只读 scope 会不会写库」时，主管 AI 回答「不会」，
而它这次回答本身就写了一条会话——它的答复里那个 `sessionId` 就是证据。）

### P8 · 权限档真的在拦（B3 的 S6，核心安全承诺）

同一条工作流（entry → shell 脚本 → end，脚本写一个探针文件），
只改权限档跑两次：

| 权限档                | 运行状态           | 当前节点 | 探针文件（脚本执行了吗） |
| --------------------- | ------------------ | -------- | ------------------------ |
| `review_every_change` | `waiting_approval` | `sh`     | **不存在（没执行）**     |
| `workspace_safe`      | `succeeded`        | —        | 存在（执行了）           |

**引擎真的按档位办事**，不是界面上的假安全感。
挂起发生在脚本**执行之前**（探针文件不存在能证明这一点——
拦晚了的话文件已经写了）。

## 数据不可用的一项

**令牌越界扫描**：脚本报每屏 14–18 种「越界颜色」、字体「Phosphor」，
**这是误报**——设计系统大量使用 `color-mix()`，计算出来的中间色不在令牌表里；
Phosphor 是图标字体，本来就该出现。

总纲 §3.5 里那段脚本的判据对这套设计系统**过严**，需要改成「只查
`getComputedStyle` 拿到的原始自定义属性」或者交给人眼。
这一项这一轮**没有结论**。
