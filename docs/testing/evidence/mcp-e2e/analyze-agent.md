方案清单（按改动面和风险从小到大）：

1. 热重载成功后主动失效受影响的缓存项（推荐）

   - 改动点：watcher 成功解析并发布新快照后，删除变更 key 的 TTL 缓存；如果无法可靠计算差异，则清空配置缓存。执行顺序必须是“发布新快照 → 失效缓存 → 宣告 reload 完成”。
   - 风险：全量清空可能短时降低命中率；按 key 清理则可能遗漏嵌套配置、别名或派生 key。若读请求能穿插在发布与清理之间，仍可能短暂读到旧值。
   - 怎么验证：先缓存 `x=old`，修改为 `x=new`，等待 watcher 的完成信号，再断言读取为 `new`；同时验证未变化 key、配置删除、解析失败保留旧快照。并发执行该场景并运行竞态检测。

2. 给缓存项绑定配置快照版本

   - 改动点：每次成功热重载递增 generation/version；缓存项记录生成它的版本，`getConfig` 只接受与当前快照版本一致的缓存。
   - 风险：改动涉及 watcher、快照和缓存读取链路；版本与快照必须原子发布，否则会出现新版本配旧快照。旧缓存还需要回收。
   - 怎么验证：连续快速重载多个版本，确保 reload 完成后永远不会返回较早版本；加入高并发读写测试并运行 race detector；验证失败的 reload 不递增版本。

3. 移除 `getConfig` 的二级 TTL 缓存

   - 改动点：直接从内存配置快照读取；如果快照本身已经常驻内存且支持原子替换，TTL 缓存可能没有必要。
   - 风险：改动面最大，可能影响吞吐、对象分配或依赖缓存副作用的调用方；需要先确认快照读取成本。
   - 怎么验证：跑现有配置测试和热重载端到端测试；对比修改前后的吞吐、延迟和内存分配；检查所有调用方是否依赖 TTL 行为。

在拿到代码前，我建议优先验证方案 1；它最贴合现象且改动最小，但目前只能算高概率判断，不能算已经完成代码级根因确认。
