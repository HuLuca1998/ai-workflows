## 第一部分：逐条复测

### 1. 首次配置：已修复

复现步骤：

1. 进入“首次配置”，确认底部有“授权工作目录并开始”“仅检测，不安装”“导出脱敏诊断报告”三个动作。
2. 点击“仅检测，不安装”，页面保持在首次配置并完成环境检查。
3. 再次进入该页，点击“授权工作目录并开始”。
4. 返回首页后检查顶栏、侧栏和底部环境状态。
5. 用只读 SQLite 查询 `workspace_setting`。
6. 再次进入首次配置，点击“导出脱敏诊断报告”。

实际结果：授权按钮返回首页；界面显示工作目录 `~/Library/Application Support/AI Workflows`、权限档 `Review Every Change` 和最新环境检查时间。数据库中 `workdir`、`permissionPreset=review_every_change`、`envCheckedAt` 三项的更新时间同步变为本轮操作时间。诊断按钮也明确提示文件已导出到 `/Users/luca/aiwf-local-test/data/diagnostics/env-diagnostics.json`。

判断：上一轮“按钮承诺开始但配置状态不落地”的断点已闭环。

### 2. 🔴 主管 AI：部分修复，能结束但仍慢且不理解当前应用

复现步骤：

1. 首页点击“询问 AI”。
2. 保留默认模型，输入“第一次使用时，我应该怎样创建并运行一个最简单的工作流？”并发送。
3. 等待 22 秒，观察状态。
4. 重新打开会话，手动选择“UI 登记的模型 1785211220166”，输入“这个应用里的最简单工作流应该如何创建和运行？请只回答界面操作。”并发送。
5. 等待请求自行结束并计时。
6. 另发一条“请用一句话解释这里的工作流是什么。”，1.2 秒后点击“取消”，再观察 0.8 秒。

实际结果：

- 默认模型请求在 22 秒时仍显示“正在想…已等待 22 秒”。
- 手动选择的 Sonnet 配置最终在 41.2 秒结束，不再无限挂死；但回复称“目前我对这个应用一无所知”，要求放开 `ls`、提供项目路径或截图。它没有回答界面里明明可见的“新建工作流 → 编辑 → 运行”步骤，与面板的“掌握全部功能”承诺相反。
- 取消操作能让等待态消失并恢复“发送”，但消息区只剩原问题，没有“已取消”、取消时间或原因。

判断：底层死锁看起来缓解了，所以不是“仍然永不返回”；但 41 秒等待、缺少应用上下文和取消无回执仍使首次求助路径基本走不通，故标为部分修复。

### 3. 🟡 新建立即持久化空草稿：仍存在

复现步骤：

1. 首页点击“新建工作流”。
2. 不改名、不拖节点、不点保存，记录 URL、标题和保存状态。
3. 返回首页，再重复一次。
4. 用只读 SQLite 按两个 URL 中的 ID 查询 `workflow`。

实际结果：两个页面分别是 `wf_bf40100880599f5b` 和 `wf_5d7b8a42fd5acc08`，都立即显示“草稿 · rev0 / 已保存”。数据库中也已有两条记录，创建时间分别为 14:59:51 和 14:59:52。

判断：与第一轮一致，用户尚未表达保存意图就会产生持久空草稿。

### 4. 执行记录输入即搜：已修复

复现步骤：

1. 进入“执行记录”，确认初始显示“历史 · 50”。
2. 在搜索框输入“Codex UX 闭环 20260728-1340”。

实际结果：列表自动变成“历史 · 4”，四条都是目标工作流。搜索框不再需要额外提示“按 Enter”，因为输入本身已经生效。

### 5. Shell 产物预览：已修复

## 第二部分：自由使用——提示词资源库与模型选择

这一轮没有再走“搭节点并运行”的主链，而是把自己当成要维护 AI 资源的用户，实际浏览模型库、在主管 AI 里选模型，并从零创建一条提示词模板。

### 实际使用路径

1. 打开“模型”，浏览第一页 `1–50 / 共 70 条`，再进入第二页 `51–70`。
2. 打开主管 AI 的模型下拉，逐项检查可选项。
3. 进入“提示词库”，点击“新建提示词”。
4. 新建“Codex Round 2 提示词 1785222114277”，得到 Role / Task / Context / Constraints / Output contract 五段骨架和 v1。
5. 分别填写五段；Task 中写入 `请用三句话解释 {{topic}}。`。
6. 点击“保存新版本”，确认卡片变为 v2；刷新页面并重新搜索该名称。
7. 依次查看“变量”“预览”“版本”三个页签。

顺畅的部分：

- 新建入口、分组和五段骨架都很清晰；“保存新版本”比普通“保存”更准确地表达了动作后果。
- 保存后列表立刻从 v1 变 v2；刷新并重新搜索后，五段内容逐字保留。
- 搜索同样是输入即生效，约半秒就只剩目标提示词。
- “预览”没有展示一个假的静态结果，而是明确说明要等真实 AI 运行提供上下文后，才会替换变量并估算 token，这个空状态可信。

### 🔴 主管 AI 的模型下拉只取前 50 条，第二页已启用模型无法选择

复现步骤：

1. 进入“模型”，确认第一页底部为 `1–50 / 共 70 条`。
2. 点击“下一页”，确认第二页存在并启用了 `[基线] Sonnet 5 · medium`、`[基线] Opus 5 · high`、`[基线] Codex · high`。
3. 返回首页，打开“询问 AI”。
4. 展开模型下拉并检查全部选项。

实际结果：下拉恰好只有 50 个选项，三个已启用的基线模型一个都没有。页面文案说“系统内所有模型下拉只列出这里已启用的条目”，但实际行为是“只列模型列表第一页中的条目”。用户想用第二页的某个已启用模型时没有可行路径。

### 🟡 提示词“变量”页没有创建入口，也没有占位符语法说明

复现步骤：

1. 新建提示词，在 Task 中输入 `请用三句话解释 {{topic}}。`。
2. 保存新版本。
3. 查看左侧卡片和“变量”页签。

实际结果：卡片仍显示“0 变量”；变量页只有“变量 / 运行时来源 / 缺失时”三个表头和 Secret 说明，没有“添加变量”按钮、输入框，也没有告诉用户支持哪种占位符语法。因此无论 `{{topic}}` 是正确还是错误写法，用户都无法从界面学会怎样把它声明成变量。

### 🟡 “版本”页只有当前版本，无法查看刚刚被替换的 v1

复现步骤：

1. 创建提示词，确认初始为 v1。
2. 填写内容并点击“保存新版本”，确认变为 v2。
3. 打开“版本”页签。

实际结果：页面只显示 `v2 · 当前` 和时间，没有 v1 的条目、内容差异或恢复入口。底部文案强调“运行记录会引用当时的提示词版本，历史结果始终可解释”，但资源库本身不能查看前一个版本；“保存新版本”的可理解性因此打了折扣。

## 处理结果（Claude 回填）

| 结论                             | 处理                                                                                                                                                                                     | 验证                                                                  |
| -------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------- |
| 🔴 模型下拉只取前 50 条          | 我加分页时引入的回归：下拉与列表页调同一个方法，而分页默认 limit=50 是给列表页定的。两处「列全部已启用」显式写上 `limit`。加守卫扫源码：带 `enabledOnly` 却不带 `limit` 的调用一律判失败 | 3 条守卫用例                                                          |
| 🔴 主管 AI「对这个应用一无所知」 | 属实，而且抽屉顶上写着「掌握全部功能」—— 提示词里一个字都没提这个应用是什么。补上应用说明：是什么、八个屏各做什么、草稿与版本的区别、以及「不能发布也不能运行」的权限边界                | 实测它给出可照做的界面步骤，并主动说明发布和运行只有用户能做（24 秒） |
| 🔴 取消无回执                    | 按了取消界面上什么都没变化，和没按上一样。现在留一条「等待 N 秒后已取消」                                                                                                                | 2 条用例                                                              |
| 🟡 空草稿立即落库                | **不改**，理由见 [ux-round1a](ux-round1a-codex.md)：曾在离开时自动丢弃，React 双次挂载让它跑在用户动手之前，用户刚拖的节点存进了已删的工作流                                             | 2 条回归用例守着别再加回去                                            |
| 🟡 提示词变量页无创建入口        | 待办，属 M3（AI 能力）                                                                                                                                                                   | —                                                                     |
| 🟡 版本页只有当前版本            | 待办，属 M3                                                                                                                                                                              | —                                                                     |

## 总体感受

第一轮最明确的工程断点大多修得扎实：首次配置真正落地、搜索变成输入即搜、Shell 输出能预览、默认名称也可靠递增。提示词库的五段编辑与刷新持久化同样顺手，空状态文案比很多工具诚实。

当前最影响真实使用的是主管 AI：它最终能结束请求，但响应仍慢，且不知道自己所在应用的界面与功能；模型超过 50 条后，主管下拉又会把第二页已启用模型完全挡住。提示词库的变量和版本页属于次一级问题，主编辑能用，但这两个页签目前更像只读占位，无法完成它们名称所承诺的管理动作。
