# 测试规约

**功能以测试先行为基准。** 这不是口号，是本项目的施工顺序：
先写下期望行为的测试，再写实现。

## 为什么这么做

这个软件的价值全在「可解释、不越权、可恢复」上。这三件事有个共同点：
**出问题时用户往往察觉不到**——路径守卫漏了一个符号链接、脱敏漏了一种 Token 形态、
事件流少了一段 seq，界面照样正常显示。只有测试会替你发现。

所以测试先行在这里不是风格偏好，是这类缺陷的唯一发现手段。

## 顺序

1. **先写测试**，用它描述期望的行为与边界。测试名写成完整的一句话，说明「应该怎样」。
2. **跑一遍，确认它失败**——失败信息本身也是产物，要能看懂。
3. **再写实现**，让它通过。
4. 重构时保持测试不变；测试要改说明契约变了，那要走 [CONTRIBUTING.md](CONTRIBUTING.md) 的契约变更流程。

## 什么必须有测试

| 类型                                      | 要求                                                     |
| ----------------------------------------- | -------------------------------------------------------- |
| 契约（`packages/contracts`）              | 每个导出都要有测试。它是三方共用的真源，改错的代价最大   |
| 安全基元（PathGuard、Redactor、能力校验） | 每种绕过方式都要有一条用例。新发现一种就补一条           |
| 状态机                                    | 合法迁移、终态无出边、可恢复状态集合                     |
| 存储层                                    | 约束真的生效（唯一、外键、级联），而不只是「代码里写了」 |
| 事件投影                                  | 乱序、重复、断流、重试轮次                               |
| UI 组件                                   | 无障碍关联（label / aria）、空态、禁用态、键盘操作       |
| 踩过的坑                                  | 修一个坑就补一条测试，避免重构时踩回去                   |
| **接缝**                                  | 见下一节 —— 这是本项目最缺的一类                         |

## 接缝测试：这个项目栽得最狠的地方

单侧测试全绿而功能不工作，是本仓库最常见的缺陷形态。
[DEBT.md](DEBT.md) 里 7 条坏账有 5 条是这么来的。

典型形态：契约声明了一样东西，前端实现了消费侧并且测得很认真，
后端从不产出它——**两侧各自的测试都绿，合起来看像一条通的链路**。

```ts
// packages/client-core/tests/event-store.test.ts —— 测试自己造事件喂投影
ev({ type: 'node.queued', seq: 5, nodeId: 'n1', attempt: 1 }),
```

投影处理得完全正确，测试绿。而引擎从不发 `node.queued`。

契约能声明三样东西，**三样都要有接缝守卫**：

| 声明的东西 | 接缝守卫要断言什么                                                 |
| ---------- | ------------------------------------------------------------------ |
| 节点类型   | 在 `IMPLEMENTED` 里 ⇔ executor 有专门分派分支且不是空操作          |
| 配置字段   | 每个 configSchema 顶层字段在引擎里有消费点，或在白名单里并显示提示 |
| 事件类型   | 每个声明的事件类型在引擎/core-api 里至少有一个发射点               |

有意暂不实现的进白名单**并写明理由**，照 `crates/mcp/src/catalog.rs`
的 `DELIBERATELY_HIDDEN` 那个做法。

## 守卫本身要有测试

**守卫不能证明自己会红，就不是守卫。**

界面审查曾一次性发现五道假守卫：状态机门禁不读契约只比硬编码字面量；
DTO 漂移守卫只认名字带 `Dto` 的结构体，漏了 12 个；禁用内部代号的正则
只认三种写法，JSX 换行即绕过。

> 它绿着，给人「这类问题以后不会再有了」的保障，但保障的范围只覆盖了
> 恰好已经修掉的那几处的写法。**比没有测试更糟：没有测试至少不会有人以为它被守住了。**

所以每加一道门禁，配一条**故意违反它、断言它变红**的元测试。
`packages/contracts/tests/` 与 `apps/web/tests/no-internal-jargon.test.ts` 里有现成例子。

## 测试自己也会假装成功

上一节说的是**门禁**要能证明自己会红。这一节说的是：**每一条测试都会**。

2026-07 那几轮复核里，我自己写的修复配套测试有相当一部分是假的 ——
它们绿着、跑在 CI 里、看起来在守着刚修好的那个坑，而实际上
把实现整个删掉它们照样绿。这不是手滑，是有固定形态的，认得出来：

| 形态                             | 长什么样                                 | 那次的实例                                                                                           |
| -------------------------------- | ---------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| **mock 没起来**                  | 依赖外部进程的测试跑得飞快               | 10 条 ACP 会话测试 0.29 s 跑完 —— hang mock 一次都没被调起；改真之后 10.13 s                         |
| **注入了本该验证的状态**         | `setup` 里直接把结果塞进 store           | `从('/runs?run=run_1')` 之前先 `reset({selectedId:'run_1'})` —— `?run=` 这条路径从没被读过           |
| **断言是同义反复**               | 断言的东西就是实现那一行                 | `shutdown()` 之后断言 `live_count()==0`，而 shutdown 的实现就是 `live.clear()`                       |
| **判据匹配不到任何真实写法**     | 正则/字符串扫描，从没命中过              | `/setTimeout\([^)]*\bquery\b/` 在 `setTimeout(() => {` 的第一个 `)` 处就截断了                       |
| **走的是测试专用入口**           | 用了一个生产零调用的 setter              | `with_capabilities()` 只有测试传过，五条「能力校验是硬的」证明的是一条运行时走不到的路径             |
| **构造了契约里不可能的形状**     | 手写 config 塞进一个 schema 里没有的字段 | 往 `script.shell` 的 config 塞 `agentProfileId` —— Zod 的 strip 语义会丢掉它，界面根本存不出这个形状 |
| **循环里 `continue` 跳过了全部** | 按键名挑用例，键名一改就一条不比         | conformance 的 43 组夹具可以静默变成 0 组，`夹具不是空的` 拦不住                                     |
| **异步没等**                     | 同步断言一个 effect 里的结果             | 选中是 `load().then(select)`，`expect` 在它落地前就跑完了                                            |

### 唯一可靠的验收：元测试

写完一条测试，**把实现改坏，确认它变红**。这一步没做，这条测试就不算数。

改坏的方式要对准它自称在守的那件事：

- 修了 `shutdown` 主动 kill 进程 → 退回「只 `live.clear()`」，看红不红
- 加了防连点的 ref 锁 → 把 `if (inFlight.current)` 换成 `if (running)`，看红不红
- 让 Dry Run 用角色的 runtime → 退回「自己读 `node.config.runtime`」，看红不红

**元测试的结论要写进提交信息**，包括「哪条抓得住、哪条抓不住」。
那次两条测 shutdown 的用例里，只有一条在退化版下会红，另一条走的是
Drop 路径 —— 注释里必须写明它守的是哪一条，否则下次又会被当成护栏。

### 附带的几条经验判据

- **耗时是证据**。一套涉及起进程、连 adapter、跑真实脚本的测试如果毫秒级跑完，
  先怀疑 mock 没起来，而不是庆祝速度
- **测试里的巧合要主动消除**。`只挂角色不写节点 runtime 时按角色查`
  一开始用 `acp.claude` 做角色 runtime，恰好等于旧实现的缺省值 ——
  它在退化版下照样绿。换成 `acp.codex` 才有区分度
- **性能断言要验证它抓得住退化**。FTS 那条一开始阈值 3 s，
  把实现退回全表扫之后实测 3.18 s —— 照样绿。收紧到 1.2 s 并双向验过
  （0.36 s 通过 / 2.8 s 失败）才算数
- **测试之间会互相清场**。页面加载时的 `run.list` 会把 store 的 items 清空，
  于是点击落在一个已经消失的按钮上，而断言看起来像是「防连点生效了」
- **`fireEvent` 每次都会 flush 一轮更新**。要覆盖「React 还没重渲染」
  那个窗口（ref 锁存在的唯一理由），必须在同一个 `act` 批次里派发多次原生事件

## 死代码会伪装成防线

第四道接缝守卫（`crates/engine/tests/capability_reach_test.rs`）守的是
一种新形态：**代码写了、编译过、测试也有，但运行时一次都到不了**。

`check_capability` 里给 `script.shell` / `git.worktree` 写的三支分支
永远匹配不到 —— 能力从 `profile_for(node)` 取，而它只认 config 里的
`agentProfileId`，这几种节点的 configSchema 里根本没有这个字段。
于是「Agent 角色」页顶上那句「权限（引擎强制，Prompt 无法越权）」
对脚本节点是假话：用户把「命令」调成「不允许」，脚本照跑。

前三道守卫问的是「契约声明了的，引擎实现了没有」。
这一道问的是反过来的那半句：**「引擎实现了的，够得着吗」**。

加分支、加校验、加拦截之前，先确认它的输入在生产里真的会到达。
够不着的防线比没有防线糟 —— 它会让下一个人（包括你自己）
在错误的安全假设上继续加东西。

## 什么不必写测试

- 纯转发、纯类型声明、常量表本身
- 像素级布局（用组件画廊看）
- 第三方库的行为

## 怎么写

**测试名说明「应该怎样」，不是「测什么」**：

```ts
// 好：读了就知道系统承诺什么
it('符号链接指向根外被拒——这是最容易漏的一条', ...)

// 差：没有信息量
it('test symlink', ...)
```

**断言失败时要能自解释**。带上实际值：

```rust
assert!(matches!(err, GuardError::Escape { .. }), "实际：{err:?}");
```

**用真实数据，别用 mock 喂 mock**。存储层测试用真的 SQLite（内存库），
路径测试用真的临时目录与真的符号链接。

## 命令

```bash
pnpm test              # 全部 TS 测试
pnpm test:cov          # 带覆盖率
pnpm rs:test           # 全部 Rust 测试
pnpm verify            # 提交前的完整门禁（等价于 CI）
pnpm test:e2e          # Playwright
```

单个包：`pnpm vitest run --project contracts`、`cargo test -p aiwf-engine`。

## 质量门禁

| 门禁                                      | 守的是什么                                     |
| ----------------------------------------- | ---------------------------------------------- |
| `pnpm test` / `cargo test`                | 行为不回退                                     |
| `pnpm contracts:check`                    | 契约生成物与源一致——手改 `generated/` 会被打回 |
| `cargo test -p aiwf-engine contract_sync` | Rust 镜像没有脱离契约                          |
| `cargo test -p aiwf-engine conformance`   | Rust 的 patch/validate/diff 与 TS 逐字等价     |
| `pnpm lint` / `cargo clippy -D warnings`  | 代码风格与常见错误                             |
| `node scripts/scan-secrets.mjs`           | 仓库里没有明文凭据                             |
| `pnpm --filter @aiwf/web build`           | 构建没坏                                       |

`pnpm lint` 目前只有 4 条规则是 `error` 级，warning 不会让门禁变红 ——
见 [DEBT.md](DEBT.md) 的 L-3。

覆盖率门槛 70%。**覆盖率是下限不是目标**——覆盖到了不等于测对了。

## 自动化测不到的那一层

「拖起来卡不卡、翻页找不找得到、这个东西看着能点其实点不动」——
自动化断言回答不了这类问题，需要真的去点。

判定标准必须量化，否则会被自己说服：

| 项           | 标准                                       |
| ------------ | ------------------------------------------ |
| 拖动帧率     | ≥55 fps，最长帧 ≤50ms                      |
| 主操作入口   | 滚动 0px 可见                              |
| 响应 >1s     | 必须有中间态且可取消                       |
| 可点元素三问 | 想不想点 / 点得动吗 / 点完给的是不是他要的 |

两条纪律：

- **要真的点**。看不到就是 FAIL，不能因为「代码里写了所以应该对」判 PASS
- **报告不等于缺陷**。每条都要自己复现一次再判——曾有两轮都没能复现的报告，
  写了 e2e 往返测试压着，至今是绿的

历史审查的完整方法与教训见 [archive/审查历史.md](archive/审查历史.md)，
六角色剧本在 [archive/ui-cases/](archive/ui-cases/)。

## 复核自己的修复：换一个会话，专挑刚改过的地方

「一个会话一个角色」这条纪律（见上一节）在**复核修复**时同样成立，
而且更要紧：写修复的那个会话已经带着「我知道它为什么对」的答案，
再让它去找问题，找到的只会是它已经想到的那几种。

2026-07 那几轮跑下来，起作用的做法是：

1. 每一轮派一个**独立会话**的探索 agent，指令里明确「专挑上一轮刚改过的地方看」
2. 给它读 `docs/REVIEW-LOOP.md` 的「已经做完的」那一节，
   并要求**不要重复报告清单里已有的条目**
3. 要求每条发现给出：文件:行号、复现路径（用户做什么会撞上）、
   以及**它验证这条属实的方式**；拿不准的标「未验证」，不许写成结论
4. 只读探索：不改文件、不建临时文件
   （有两轮的 agent 留下了 `zz_tmp_probe_test.rs` 和一份根目录报告，
   前者被 `git add -A` 扫进提交，后者卡了 prettier）

**这个机制的实测产出**：第 7 轮那个 agent 报的四条命中，
三条是写它的那个会话（我）上一轮刚提交的东西 ——
包括两条假测试和一个「把看得见的卡死换成看不见的孤儿进程」的修复。
同一个会话自查是查不出这些的。

推论：**别把「我刚修完还跑了 verify」当成验收**。
`pnpm verify` 只回答「已有断言成不成立」，而问题恰恰出在断言本身。

## ACP：测试与试验一律优先 codex

**不要用 claude 的 adapter 做测试和试验。**

这个应用本身跑在 Claude Code 里开发。用 `acp.claude` 去测，会与开发环境
撞在一起：嵌套的 agent 会话、共用的登录态、同一份配额。跑一次测试就可能
把正在进行的开发会话搅乱，而那种干扰的表现（会话莫名其妙断掉、
配额突然见底）离原因很远。

| 位置                     | 约定                                               |
| ------------------------ | -------------------------------------------------- |
| `AGENT_RUNTIMES`（契约） | `acp.codex` 排第一，默认值与探测顺序都跟着它       |
| AI 节点没指定 runtime 时 | 用 `acp.codex`                                     |
| 主管 AI                  | `preferred_acp_runtime()` 从装好的里挑，codex 优先 |
| 新建 Agent 表单          | 默认选 Codex（ACP）                                |
| 手工试验、脚本、e2e      | 显式写 `acp.codex`                                 |

「尽可能」不是「绝不」：只装了 claude adapter 的机器上仍然要能用 ——
`preferred_acp_runtime()` 会退回到它，而不是报「没装」。

接入前先跑 `docs/acp/reference/probe.ts`：那份经验里 codex 侧
只在旧版本验证过，「某能力不支持」的结论会过期。

## 端到端：对着真实仓库跑

`crates/engine/tests/template_e2e_test.rs` 拿**真的 gh、真的 git、
真的 worktree** 跑内置模板，对着 `HuLuca1998/aiwf-e2e-fixture`
的 issue #8（一个真实的编码任务：重试的指数退避没生效）。

### 为什么不 mock 掉 gh

要验的恰恰是「配置里写的那个引用，插值之后交给 gh 能不能用」。
mock 掉就只剩下「插值函数会不会插值」，而那已经有单测了。

用户实测的 `run_18c740d6394b3c70` 死在这里：模板写
`gh issue view "$ISSUE"`，而引擎注入的环境变量叫 `AIWF_ISSUE` ——
两个都是空串。当时所有测试都是绿的，因为**没有一条站在
「配置里写的引用」与「引擎认得的引用」之间**。

### AI 节点不在这条里

跑它们要真实模型与配额，而且会与开发环境撞（CLAUDE.md 那条
「测试与试验优先用 codex」说的就是这个）。AI 节点由
`executor_test` 与 `approval_gate_test` 用 `tests/fixtures/acp-mock.mjs`
覆盖 —— 那个 mock 说的是与真实 adapter 完全相同的协议。

### 跳过要说出来

没装 gh、没登录、没网络时**跳过而不是失败** —— 这条在 CI 与离线
开发机上都跑不了，让它红只会教人忽略红灯。但跳过时 `eprintln!`
一行 `[跳过] …`：静默通过的话，没人知道这条从来没跑过。

### 怎么验证它是真的

把用户那次的原始 bug 改回去，它必须变红：

```bash
# 读 Issue 改回 $ISSUE / $REPO
# → 「读_issue_那一步真的读得到」FAILED
# worktree 的 repoRoot 改回 ${input.repo.name}
# → 「worktree_那一步在真实仓库上建得起来」FAILED
```

两条都验过。
