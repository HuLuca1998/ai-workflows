# 测试规约

**功能以测试先行为基准。** 这不是口号，是本项目的施工顺序：
先写下期望行为的测试，再写实现。

## 为什么这么做

这个软件的价值全在「可解释、不越权、可恢复」上。这三件事有个共同点：
**出问题时用户往往察觉不到**——路径守卫漏了一个符号链接、脱敏漏了一种 Token 形态、
事件流少了一段 seq，界面照样正常显示。只有测试会替你发现。

所以测试先行在这里不是风格偏好，是这类缺陷的唯一发现手段。

## 顺序

1. **先写测试**，用它描述期望的行为与边界。测试名写成完整的一句话，说明「应该怎样」。
2. **跑一遍，确认它失败**——失败信息本身也是产物，要能看懂。
3. **再写实现**，让它通过。
4. 重构时保持测试不变；测试要改说明契约变了，那要走 [CONTRIBUTING.md](CONTRIBUTING.md) 的契约变更流程。

## 什么必须有测试

| 类型                                      | 要求                                                                      |
| ----------------------------------------- | ------------------------------------------------------------------------- |
| 契约（`packages/contracts`）              | 每个导出都要有测试。它是三方共用的真源，改错的代价最大                    |
| 安全基元（PathGuard、Redactor、能力校验） | 每种绕过方式都要有一条用例。新发现一种就补一条，不要只改实现              |
| 状态机                                    | 合法迁移、终态无出边、可恢复状态集合                                      |
| 存储层                                    | 约束真的生效（唯一、外键、级联），而不只是「代码里写了」                  |
| 事件投影                                  | 乱序、重复、断流、重试轮次                                                |
| UI 组件                                   | 无障碍关联（label / aria）、空态、禁用态、键盘操作                        |
| 踩过的坑                                  | 修一个坑就补一条测试，避免重构时踩回去（见 `services/acp-sidecar/tests`） |

## 什么不必写测试

- 纯转发、纯类型声明、常量表本身
- 布局像素（那是设计走查的事，用组件画廊看）
- 第三方库的行为

## 怎么写

**测试名说明「应该怎样」，不是「测什么」**：

```ts
// 好：读了就知道系统承诺什么
it('符号链接指向根外被拒——这是最容易漏的一条', ...)

// 差：没有信息量
it('test symlink', ...)
```

**断言失败时要能自解释**。带上实际值：

```rust
assert!(matches!(err, GuardError::Escape { .. }), "实际：{err:?}");
```

**用真实数据，别用 mock 喂 mock**。存储层测试用真的 SQLite（内存库），
路径测试用真的临时目录与真的符号链接。

## 命令

```bash
pnpm test              # 全部 TS 测试
pnpm test:cov          # 带覆盖率
pnpm rs:test           # 全部 Rust 测试
pnpm verify            # 提交前的完整门禁（等价于 CI）
```

单个包：`pnpm vitest run --project contracts`、`cargo test -p aiwf-engine`。

## 质量门禁

CI 的每一项都对应一条产品承诺（功能文档 §14）：

| 门禁                                      | 守的是什么                                     |
| ----------------------------------------- | ---------------------------------------------- |
| `pnpm test` / `cargo test`                | 行为不回退                                     |
| `pnpm contracts:check`                    | 契约生成物与源一致——手改 `generated/` 会被打回 |
| `cargo test -p aiwf-engine contract_sync` | Rust 镜像没有脱离契约                          |
| `pnpm lint` / `cargo clippy -D warnings`  | 代码风格与常见错误                             |
| `node scripts/scan-secrets.mjs`           | 仓库里没有明文凭据                             |
| `pnpm --filter @aiwf/web build`           | 构建没坏                                       |

覆盖率门槛当前是 70%（基座阶段），随功能补齐逐步抬高。
**覆盖率是下限不是目标**——覆盖到了不等于测对了。

## 还没有但计划要有

按里程碑补齐（见 [ROADMAP.md](ROADMAP.md)）：

- M2：引擎集成测试（脚本 + 审批 + worktree + ACP mock），断电模拟后恢复到同一检查点
- M1/M2：性能基准（200 节点画布拖拽 60fps、10 万事件滚动、流式输出帧率），WKWebView 与 Chromium 各跑一次
- M3：ACP 兼容性探针（升级 adapter 后复跑，结论会过期）
- M5：诊断包不含 Secret 的端到端校验

## 用户操作级测试（codex 循环）

单元测试与 e2e 证明不了「这个功能被真人用起来顺不顺手」。
那一层由 codex 以用户身份反复使用来覆盖：

```bash
bash scripts/local-test-env.sh start       # 先把环境跑起来
bash scripts/codex-ux-loop.sh --rounds 3   # 连跑三轮
```

每轮它会：先读上一轮的报告复测未修的问题，再自由使用（要求换一个
与上轮不同的角度），最后写一份编号报告到 `docs/testing/ux-round-N-codex.md`。

**报告留在仓库里**，因为它们是「这个功能被真人用过」的唯一证据。
每轮的处理结果回填到报告末尾 —— 包括**不修的**与理由。

已有的报告：

| 文件                 | 内容                                               |
| -------------------- | -------------------------------------------------- |
| `ux-audit-codex.md`  | 第一轮：主链路走查，报出管理三屏「看得见但改不了」 |
| `ux-retest-codex.md` | 复测：13 项中 11 项已修，新报 8 条                 |
| `ux-free-codex.md`   | 自主体验：报出执行记录列表的 Secret 泄露           |

**不是所有报的问题都要修**。判断依据是图纸：

- 撤销 / 重做 —— 图纸的快捷键表自己标着「（待实现）」，不修
- 事件流筛选 —— 图纸的详情区没有这个控件，加了是自作聪明
- ⌘A 全选 —— 状态栏写着它却没标待实现，**承诺了就必须存在**，修

也不是所有报的问题都成立：「登记 high 刷新变 medium」两轮都没能复现，
我写了 e2e 往返测试压着，它至今是绿的。
